# Data repositories and catalogs: the "repository of data" model and how labelling attaches to it (as of Nov 2026)

Scope: Hugging Face Hub datasets (incl. Xet/XetHub, WebDataset), DVC + DVC Studio (+ DataChain), lakeFS, DagsHub, Oxen.ai, Pachyderm, Encord Index, Labelbox Catalog, Voxel51 FiftyOne (Teams/Enterprise), Roboflow, W&B Artifacts/Tables, Google Vertex AI datasets, AWS SageMaker Ground Truth, Azure ML data labelling, and GitHub's per-extension file viewers as an analogy.

Status changes worth knowing before reading anything else (all 2025-2026):
- AWS SageMaker Ground Truth "is no longer open to new customers… we do not plan to introduce new features" — [AWS docs](https://docs.aws.amazon.com/sagemaker/latest/dg/sms-task-types.html)
- Azure ML data labelling retires on September 30, 2026; "workloads running data labeling will be deleted and associated application data will be lost"; Microsoft recommends third-party providers — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/machine-learning/how-to-create-text-labeling-projects?view=azureml-api-2). (Today is Nov 2, 2026, so it has already retired.)
- Vertex AI managed datasets docs are now titled "Gemini Enterprise Agent Platform"; the console page still splits AutoML datasets by Image and Tabular — [Google Cloud docs](https://docs.cloud.google.com/vertex-ai/docs/datasets/overview)
- XetHub was acquired by Hugging Face in Aug 2024 and is now the Hub's storage backend (default for new users/orgs since May 23, 2025), not a separate product — [HF blog](https://huggingface.co/blog/xethub-joins-hf); [HF changelog](https://huggingface.co/changelog/xet-default-for-new-users)
- Pachyderm was acquired by HPE in Jan 2023 — [HPE press release](https://www.hpe.com/us/en/newsroom/press-release/2023/01/hewlett-packard-enterprise-acquires-pachyderm-to-expand-ai-at-scale-capabilities-with-reproducible-ai.html); the latest open-source release listed is v2.12.2 on Jan 15, 2025 — [GitHub releases](https://github.com/pachyderm/pachyderm/releases)

So the two big modality-typed hyperscaler labelling services (Ground Truth, Azure ML labelling) are frozen or gone, while the active vendors are either untyped repos (HF, lakeFS, DVC, Oxen, DagsHub) or catalog + typed project (Labelbox, Encord, Roboflow).

## 1. Is the data container typed by modality or untyped? What tradeoffs does each side state?

### Takeaway
Storage/versioning containers (HF Hub repo, DVC, lakeFS, Oxen, DagsHub repo, Encord folders, Labelbox Catalog) are untyped and hold any file. The *labelling* unit is almost always typed: a Labelbox project, Roboflow project, Azure ML project, Vertex dataset or Ground Truth job fixes one media type or task type at creation, and usually can't change it. The common pattern is an untyped catalog/repo plus typed labelling projects drawn from it. Only FiftyOne (grouped datasets) and Encord (data groups) model mixed media inside one labelling unit, and both still require each slot/slice to have one media type.

### Cited Findings
**Untyped containers**
- lakeFS: a repository "represent[s] tables of various formats for tabular data, semi-structured data such as JSON or log files, or a set of unstructured objects such as images, videos, and sensor data"; lakeFS calls itself "format-agnostic" and "merges by complete files"; format-specific merge strategies are "on the roadmap" — [lakeFS docs: model](https://docs.lakefs.io/latest/understand/model/)
- lakeFS's stated reason for untyped: a labelling tool "won't track that your CSV of patient info or… ML features were updated in tandem. lakeFS will track any file… In complex projects (say, autonomous driving)… images, LiDAR point clouds, and scenario metadata; lakeFS can version all of it together, whereas the labeling platform might only cover the images and some label files" — [lakeFS blog, Sep 10 2025](https://lakefs.io/blog/integrating-labeling-tools/)
- DVC: `dvc add` targets "can be individual files, directories"; a directory gets one `.dvc` file pointing to a `.dir` manifest in cache, so there is no per-type structure — [DVC docs: add](https://doc.dvc.org/command-reference/add). Artifacts in `dvc.yaml` accept "artifacts of any `type`" as free strings — [DVC docs: dvc.yaml](https://doc.dvc.org/user-guide/project-structure/dvcyaml-files)
- DataChain (from the DVC team) argues the folder isn't enough: "It is no longer enough to designate and version a file folder as a dataset; the modern data stack demands the use of AI to create features and annotations" — [DataChain launch blog](https://www.datachain.ai/blog/datachain-release). DataChain datasets are "Typed by Construction… Schemas are Pydantic models… file references, embeddings, annotations, scores" — [DataChain docs](https://www.datachain.ai/docs/concepts/datasets). So typing moves from the container to the record schema.
- Oxen.ai: a repository is "a collection of files and folders that is versioned together"; a "Dataset" is just "a tabular file within an oxen repository" (csv, jsonl, parquet) — [Oxen docs: repositories](https://docs.oxen.ai/getting-started/data). Oxen detects a per-file data type from extension: tabular (csv/tsv/jsonl/parquet/arrow), text, image, video (mp4/mov), audio — [Oxen docs: file metadata](https://docs.oxen.ai/concepts/file_metadata)
- Hugging Face Hub: one repo can hold "PNG, JPEG, TIFF and WebP" at once, folders define splits, and a `metadata.csv/jsonl/parquet` adds columns — [HF docs: image dataset](https://huggingface.co/docs/hub/datasets-image). Repos are git-based on Xet storage, which deduplicates "at the level of bytes" — [HF docs: Xet overview](https://huggingface.co/docs/hub/xet/overview)
- DagsHub: a repo can have any number of datasources; "Different data sources can point to the same bucket (or different paths within the same bucket)… This allows you to manage different metadata tables and use cases on the same raw data" — [DagsHub docs: datasources](https://dagshub.com/docs/use_cases/data_engine/connect_datasource/)
- Encord: files live in folders, and a JSON/CSV registration can "combine multiple data types in one JSON" (keys `videos`, `audio`, `time_series`, `image_groups`, `images`, `dicom_series`, `nifti`, `scenes`, `data_groups`) — [Encord docs: register cloud data](https://docs.encord.com/platform-documentation/Curate/add-files/index-register-cloud-data)

**Typed containers / labelling units**
- Vertex AI: `metadataSchemaUri` (image_1.0.0.yaml, video_1.0.0.yaml, tabular_1.0.0.yaml, …) is "Immutable" — [Google Config Connector reference](https://docs.cloud.google.com/config-connector/docs/reference/resource-docs/vertexai/vertexaidataset); you set the objective at import with an import schema, e.g. video "classification", "object_tracking" or "action recognition" — [Vertex docs: video dataset](https://cloud.google.com/vertex-ai/docs/video-data/classification/create-dataset). Managed datasets are "required for AutoML and… optional for custom training" — [Vertex docs: overview](https://docs.cloud.google.com/vertex-ai/docs/datasets/overview)
- Ground Truth: built-in task types are grouped by Images / Text / Videos & Frames / 3D point clouds, each with its own worker template — [AWS docs: task types](https://docs.aws.amazon.com/sagemaker/latest/dg/sms-task-types.html); "The format of your input manifest file depends on your task type" — [AWS docs: point-cloud manifest](https://docs.aws.amazon.com/sagemaker/latest/dg/sms-point-cloud-input-manifest.html)
- Azure ML: you choose Media type (Image or Text) and then a task type; "After the labeling project is initialized… You can't change the task type or dataset" — [Microsoft Learn: image projects](https://learn.microsoft.com/en-us/azure/machine-learning/how-to-create-image-labeling-projects?view=azureml-api-2)
- Labelbox: Catalog holds all data rows, but a project is typed: "you will only be able to attach data rows that match the data type you set here. For example, you cannot select video… and then send image data rows to this project later" — [Labelbox: create a project](https://docs.labelbox.com/horizon/guides/create-a-project). Media types include Audio, Conversational, Document, Geospatial_Tile, Html, Image, Simple_Tile, Text, Video — [Labelbox: project SDK](https://docs.labelbox.com/horizon/developer-guides/project). The stated reason is tool availability: "The media type determines which annotation tools (bounding box, polygon, etc.) will be available" — [Labelbox: ontologies](https://docs.labelbox.com/horizon/guides/labelbox-ontology). It's also used for validation: specifying ontology `media_type` is "highly recommended… for validation and error handling" — [Labelbox: ontology SDK](https://docs.labelbox.com/horizon/developer-guides/ontology)
- Roboflow: hierarchy is "Workspace → Projects → Dataset Versions → Models"; project type (object detection, classification, instance/semantic segmentation, keypoint, multimodal) "determines how your data is structured and which model architectures you can train" — [Roboflow docs: key concepts](https://docs.roboflow.com/workspaces/key-concepts). So Roboflow types by *task*, not file type; projects that share an "annotation group" share class lists — [Roboflow docs: create project](https://docs.roboflow.com/datasets/create-and-upload/create-a-project)
- FiftyOne: every dataset has a `media_type`, and grouped datasets have `media_type == "group"`. "Grouped datasets may contain a mix of different modalities… but FiftyOne strictly enforces that each slice… must have a homogeneous media type" — [FiftyOne docs: groups](https://docs.voxel51.com/user_guide/groups.html)
- Encord: "A Project can have multiple Datasets attached to it, but only one Ontology" — [Encord docs: datasets](https://docs.encord.com/platform-documentation/Annotate/annotate-datasets/annotate-datasets)

### Inferences
- In 2026 the industry has converged on "untyped store, typed task." Where vendors give reasons for typing, they're about which tools and model architectures apply (Labelbox, Roboflow) and validation (Labelbox), not storage. Nobody argues storage should be typed.
- For the product question: "Sources" (raw files) matches the untyped repo layer everywhere. A Studio is the labelling unit, and vendors type that by modality or task. But FiftyOne and Encord show one unit can hold mixed media as long as each slot is typed and a sample can span slots.

### Gaps
- No vendor published a design doc, RFC or blog post that directly compares typed and untyped containers. The reasons above come from docs and marketing copy. lakeFS's Sep 2025 blog is the closest to an explicit argument, and it comes from the untyped side.
- Pachyderm: I found no current (2025-26) docs on its repo/branch model or labelling. HPE's product status beyond the Jan 2025 OSS release is unverified.

## 2. How does a labelling job/view attach to an untyped repo (filter/query, folder, type)? Can one queue span several file types?

### Takeaway
There are three ways to attach a labelling job: a query or selection over a catalog (Labelbox, DagsHub, DataChain/FiftyOne-style views), a folder or storage path (Encord continuous data flow, Label Studio over a lakeFS branch path, Azure/Vertex/Ground Truth via manifest or datastore), or a manifest/table of rows (Ground Truth, Oxen, HF metadata files). Queues are single-type everywhere except where the "task" itself is a multi-file composite (Encord data groups, Ground Truth custom template + Lambda, Label Studio multi-source tasks, FiftyOne groups).

### Cited Findings
- Labelbox: filter in Catalog, then "Send to Annotate" as a batch with priority 1-5 and optional consensus. "You can only send a batch to a project that has the same media type"; a batch can't be shared between projects, and a data row can't be in two batches of the same project — [Labelbox: batches](https://docs.labelbox.com/horizon/guides/batches). Up to 1M data rows per `create_batches()` call, chunked at 100k — [Labelbox: project SDK](https://docs.labelbox.com/horizon/developer-guides/project)
- DagsHub: annotate a whole datasource from the UI, select data points by hand, or filter in code (`ds.head(5).annotate()`), which is "especially useful… where you wouldn't necessarily want to redo the entire dataset's labels, but only parts". Tasks go to a new or existing Label Studio project — [DagsHub docs: annotation](https://dagshub.com/docs/use_cases/annotation/). A query on a datasource returns another datasource, which "you can save… as a dataset" — [DagsHub docs: Data Engine](https://dagshub.com/docs/feature_guide/data_engine/)
- Encord: folders can enable "Continuous Data Flow… so all files added to it are automatically added to a Project". "Mirrored Datasets" are backed by a folder and stay in sync both ways, and a file then "cannot be added to multiple Datasets" — [Encord docs: Index basics](https://docs.encord.com/platform-documentation/Curate/index-files); [Encord docs: datasets](https://docs.encord.com/platform-documentation/Annotate/annotate-datasets/annotate-datasets). Projects combine Dataset(s) + one Ontology + Workflow + collaborators — [Encord docs: data lifecycle](https://docs.encord.com/solutions-documentation/applied-ai/data-lifecycle)
- lakeFS + Label Studio: lakeFS exposes an S3 endpoint with paths `s3://[REPOSITORY]/[BRANCH]/PATH` — [lakeFS docs: AWS CLI](https://docs.lakefs.io/reference/aws-cli/). Label Studio source/target storage is "project-specific", and annotations are written both to its DB and to target storage on Submit — [Label Studio docs: storage](https://labelstud.io/guide/storage). Result: a labelling project attaches to *a folder on a branch*. "if a labeling tool can work with your cloud bucket, it can likely work with a lakeFS repository" — [lakeFS blog](https://lakefs.io/blog/integrating-labeling-tools/)
- Label Studio can load tasks as JSON/JSONL/Parquet from storage, "particularly helpful when dealing with complex tasks that involve multiple media sources" — [Label Studio docs: storage](https://labelstud.io/guide/storage)
- Ground Truth: "each line of the manifest describes a unit of task" — [AWS docs](https://docs.aws.amazon.com/sagemaker/latest/dg/sms-point-cloud-input-manifest.html). To mix file types in one queue, the AWS blog has each manifest line point to a JSON that references both a PNG image and a CSV of sensor data, rendered by a custom template plus a pre-labelling Lambda — [AWS ML blog: mixed-source industrial datasets](https://aws.amazon.com/blogs/machine-learning/labeling-mixed-source-industrial-datasets-with-amazon-sagemaker-ground-truth/) (older post; the date wasn't checked). Manifest lines can be up to 100 KB — [AWS docs: Lambda](https://docs.aws.amazon.com/sagemaker/latest/dg/sms-custom-templates-step3-lambda-requirements.html)
- Azure ML: image data must be in a Blob datastore, "Each file is an item to label", or an `MLTable` asset — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/machine-learning/how-to-create-image-labeling-projects?view=azureml-api-2). For text, a `.txt` file is one item, while in csv/tsv "Each row represents one item" — [Microsoft Learn: text](https://learn.microsoft.com/en-us/azure/machine-learning/how-to-create-text-labeling-projects?view=azureml-api-2)
- Oxen: "Build a dataset from this folder" collects every file into a parquet with a `file_path` column, and captioning/labelling runs over that table ("Run Inference" or the fine-tune wizard's "Label Data" step) — [Oxen docs: video generation](https://docs.oxen.ai/examples/fine-tuning/video_generation)
- Roboflow: labelling happens inside a project typed by task; there's no cross-project queue — [Roboflow docs](https://docs.roboflow.com/workspaces/key-concepts)
- DVC itself has no labelling attachment. A DVC forum user "opted for a combination of DVC and fiftyone"; the DVC maintainer pointed to DataChain for linking labels to files — [DVC forum](https://discuss.dvc.org/t/managing-labels-annotations/2340) (older thread, date not checked)

### Inferences
- "Attach by query" (Labelbox, DagsHub) and "attach by folder" (Encord continuous flow, Label Studio over a lakeFS path) both exist. Query-based attachment lets one raw store feed many typed projects. Folder-based attachment is simpler and live, but ties a file's location to its workflow. Encord's mirrored dataset trades flexibility for simplicity in exactly this way, in its own words.
- No surveyed product offers a single queue whose items are heterogeneous single files (an image task followed by an audio task in one queue) through one UI. Mixed queues only exist when every task is the same multi-file composite.

### Gaps
- I didn't verify whether an Encord Project can mix modalities across its attached Datasets (e.g. one image dataset plus one audio dataset). A search summary claimed it can, but the primary doc text I read only says "multiple Datasets… only one Ontology". Treat it as unverified.
- DVC Studio's current UI for datasets/labels: I found no 2025-26 docs showing a labelling attachment. It appears to be an experiment/model registry UI over Git + DVC.

## 3. How do they handle "one sample = several files" (pairs, sidecars, series)?

### Takeaway
There are four patterns: (a) a sidecar metadata table keyed by relative path (HF `metadata.*` with `file_name`/`*_file_name`, Oxen/DataChain/DagsHub path columns), (b) shared filename prefixes inside a shard (WebDataset `000.jpg` + `000.json`), (c) a first-class group/composite object with typed slots (FiftyOne groups, Encord data groups/image groups/DICOM series, Ground Truth sequence files), and (d) one manifest row pointing at a JSON that lists several files (Ground Truth custom, Label Studio tasks).

### Cited Findings
- HF: a metadata file must sit in the same or a parent directory of the files it describes; "any column named `file_name` or `*_file_name` should contain the full relative path". "Metadata files cannot be put in subdirectories of a directory with the images" — [HF docs: image dataset](https://huggingface.co/docs/hub/datasets-image). The `*_file_name` suffix allows several file columns per row, which is how pairs are expressed.
- WebDataset on HF: TAR shards of about 1 GB; "Make sure each image and metadata pair share the same file prefix" — [HF docs: image dataset](https://huggingface.co/docs/hub/datasets-image)
- HF NIfTI: a 3D/4D volume is one file per example, linked by `metadata.*` with `file_name` — [HF docs: NIfTI dataset](https://huggingface.co/docs/datasets/nifti_dataset)
- FiftyOne grouped datasets: a group holds several slices (e.g. KITTI `{'left': 'image', 'right': 'image', 'pcd': '3d'}`), with a `default` slice shown in the grid. Only one `Group` field per dataset; slices are added dynamically — [FiftyOne docs: groups](https://docs.voxel51.com/user_guide/groups.html). Marketing copy adds that "Groups don't require a shared timeline" — [Voxel51 FiftyOne page](https://voxel51.com/fiftyone)
- Encord: "Data groups let you combine multiple data items… into a single annotation task with a multi-pane layout", with layouts `default-grid`, `default-list` (carousel) or `custom` split panes — [Encord docs: register cloud data](https://docs.encord.com/platform-documentation/Curate/add-files/index-register-cloud-data). Upload can also batch images into an "image group or image sequence", and DICOM series require Study/Series/SOP instance UID tags — [Encord docs: Index basics](https://docs.encord.com/platform-documentation/Curate/index-files)
- Ground Truth point-cloud tracking: each manifest line is a sequence JSON with `seq-no`, `prefix`, `number-of-frames`, and a `frames` list (each with `unix-timestamp`, frame path, optional camera fusion data) — [AWS docs: sequence manifest](https://docs.aws.amazon.com/sagemaker/latest/dg/sms-point-cloud-multi-frame-input-data.html)
- Ground Truth mixed sources: a manifest line → dataset JSON `{"sensor_data": {"s3Path": "...csv"}, "image": {"s3Path": "...png"}}` — [AWS ML blog](https://aws.amazon.com/blogs/machine-learning/labeling-mixed-source-industrial-datasets-with-amazon-sagemaker-ground-truth/)
- DataChain samples are "sparse references to files or objects inside files… features within parquet or .tar archives, tiles within the bounding boxes in images, snippets within text blobs" — [DataChain launch blog](https://www.datachain.ai/blog/datachain-release)
- Oxen dataset files "can be multi-modal containing links to images, audio, and PDFs" — [Oxen docs: datasets](https://docs.oxen.ai/examples/data/datasets)
- DagsHub keys every datapoint by path ("primary key"), and enrichments can be "arbitrary binary data" — [DagsHub docs: enrich](https://dagshub.com/docs/use_cases/data_engine/enrich_datasource/); [DagsHub docs: Data Engine](https://dagshub.com/docs/feature_guide/data_engine/). That makes a sidecar something attached to one primary file, not a peer of it.

### Inferences
- In untyped repos, the "sample" is defined by a table (sidecar or manifest) rather than by the folder. That's also the natural boundary between Sources (files) and Datasets (curated tables of references) in the product's model.
- Labelling tools that handle multi-file samples well (FiftyOne, Encord) make the group a typed object with named slots and a default/primary slot. That's the model a single mixed-folder Studio would need.

### Gaps
- I didn't confirm how the HF Dataset Viewer treats a folder of mixed modalities without a metadata file (e.g. images and audio side by side), i.e. whether it picks one folder builder or errors.

## 4. Branch/version semantics for labels vs raw data

### Takeaway
There are two camps. (a) Git-style repos (lakeFS, HF, Oxen, DVC) version labels as files next to the raw data, with branches and merges, and merge at whole-file level. (b) Platform-style tools (FiftyOne Enterprise, Roboflow, DataChain, Labelbox/Encord) version labels and metadata in a database as linear immutable snapshots, and treat the media as immutable external references.

### Cited Findings
- lakeFS: commits are immutable; branches are zero-copy pointers plus uncommitted changes; merges are three-way at file level, with conflicts resolved only by a global `source-wins`/`dest-wins` strategy. "it is currently not possible to treat conflicts individually" — [lakeFS docs: model](https://docs.lakefs.io/latest/understand/model/)
- lakeFS's labelling workflow: label on a branch (e.g. `labeling_experiment`), QA, then merge into `production`. "This one merge operation might publish hundreds of new labels to production in one atomic action"; revert by reverting the merge commit — [lakeFS blog, Sep 2025](https://lakefs.io/blog/integrating-labeling-tools/)
- FiftyOne Enterprise: "a linear sequence of read-only Snapshots", with the editable state called HEAD. A snapshot is "a commit and tag… all in one" and can only be made from HEAD. Snapshots exclude media in cloud buckets, "which are assumed to be immutable. If you need to update the image… update the sample's filepath" — [FiftyOne docs: dataset versioning](https://docs.voxel51.com/enterprise/dataset_versioning.html). Introduced in Teams 1.4 (older post) with History-tab diff, rollback and clone — [Voxel51 blog](https://voxel51.com/blog/announcing-fiftyone-teams-1-4-with-dataset-versioning-delegated-operations-and-ultralytics-integration)
- Roboflow: a Dataset Version is a snapshot of the project; "Once created, it does not change", and later edits to images or annotations don't affect it. Training targets a version — [Roboflow docs](https://docs.roboflow.com/workspaces/key-concepts)
- DataChain: every `save()` creates an immutable semver version, and `diff(…, compare=["score","label"])` shows row-level A/D/M/S status. `file_diff()` compares storage snapshots. Raw files are versioned through cloud object version IDs, not hashes — [DataChain docs: datasets guide](https://www.datachain.ai/docs/guide/datasets); [example-datachain-dvc](https://github.com/shcheklein/example-datachain-dvc)
- DVC: `.dvc` files hold md5/etag and an optional cloud `version_id`, and Git versions them. Checkout of data follows `git checkout` + `dvc checkout`, per file or for the whole workspace — [DVC docs: .dvc files](https://doc.dvc.org/user-guide/project-structure/dvc-files); [DVC tutorial](https://doc.dvc.org/example-scenarios/versioning-data-and-models/tutorial)
- DagsHub: annotations are saved as an enrichment field "named after the annotation project name… + annotation", stored as a Label Studio JSON blob, plus a derived `<name>.labels.str` field for querying — [DagsHub docs: annotation](https://dagshub.com/docs/use_cases/annotation/). The product claims "versioning that tracks all metadata changes" — [DagsHub product page](https://dagshub.com/product/curate-annotate/) (marketing)
- Oxen: branches are "A named pointer to a commit". A "Workspace" is "the equivalent of a working directory on the remote server where files can be added in an uncommitted state" — [Oxen docs](https://docs.oxen.ai/getting-started/data). Oxen turns tabular files into "a lightweight database that can be queried, edited, versioned" — [Oxen docs: datasets](https://docs.oxen.ai/examples/data/datasets)
- HF: the Parquet conversion is published on a parallel `refs/convert/parquet` branch next to `main` — [HF dataset-viewer docs](https://huggingface.co/docs/dataset-viewer/parquet)
- W&B: reference artifacts store only metadata (ETag, size, version ID if bucket versioning is on). W&B recommends enabling object versioning so artifacts keep pointing at the exact data used — [W&B docs: external files](https://docs.wandb.ai/models/artifacts/track-external-files). Tables can be logged `IMMUTABLE` (default), `MUTABLE` (each re-log is a new artifact version) or `INCREMENTAL` — [W&B docs: Table](https://docs.wandb.ai/models/ref/python/data-types/table)
- Labelbox/Dataloop-style tools: lakeFS notes that a labelling tool's versioning "is usually confined to annotating data and the dataset subsets within that platform", and cites Dataloop's "virtual versions" and data branching — [lakeFS blog](https://lakefs.io/blog/integrating-labeling-tools/)

### Inferences
- Across tools, raw media is treated as immutable and content-addressed, while labels are the thing that changes and needs history. Platforms version labels separately and linearly. Git-style repos version labels and raw data together but can't merge label files semantically (lakeFS states this limit directly).
- If the product puts labels in its repo as files, two people labelling the same file on different branches will conflict at file granularity unless labels are stored one per item or per annotation. That's the reason platforms keep labels in a DB.

### Gaps
- Labelbox and Encord label-versioning specifics (export snapshots, workflow history) weren't researched in this pass.
- I found no tool that does semantic (per-annotation) three-way merging of labels across branches.

## 5. How do browser viewers pick renderers, and what happens to files that need conversion?

### Takeaway
There are two dispatch models. GitHub, Oxen's file view and DagsHub dispatch per file by extension or detected type. HF, Oxen datasets, W&B Tables and DagsHub's dataset viewer dispatch per column by a declared feature/media type, usually on a table produced by conversion or indexing. Files that need conversion get transcoded or indexed into a browser-friendly form (HF to Parquet up to 5 GB, W&B arrays to PNG/GIF/MP4, GitHub moved to client-side libraries). Anything unsupported falls back to raw/download, or "viewer: false".

### Cited Findings
**Per-file, by extension (GitHub analogy)**
- GitHub renders `.stl` (interactive 3D), `.csv/.tsv` as searchable tables (only up to 512 KB; errors for mismatched columns or other delimiters), PDF (links ignored), GeoJSON/TopoJSON via Leaflet (`.json` only if `type` is FeatureCollection/GeometryCollection/topology), and `.ipynb` as static HTML with no JS interactivity — [GitHub docs: non-code files](https://docs.github.com/en/repositories/working-with-files/using-files/working-with-non-code-files). GitHub also offers image diffs in 2-up, swipe and onion-skin modes — [helaili/Goodies](https://github.com/helaili/Goodies) (unofficial demo repo)
- In 2022 GitHub moved notebook/GeoJSON/PDF/PSD/STL/SVG rendering from server-side to "primarily in the browser using open-source libraries like nbconvert, psd.js, and three.js" (older source) — [GitHub changelog](https://github.blog/changelog/2022-01-07-jupyter-notebooks-and-specialized-file-formats-display-faster/)
- Oxen: default type detection by extension (tabular/text/image/video/audio) — [Oxen docs: file metadata](https://docs.oxen.ai/concepts/file_metadata)

**Per-column, by declared type**
- HF Dataset Viewer: supports "text to tabular and from image to audio formats", and splits come from file/folder names or YAML `configs` — [HF docs: configure viewer](https://huggingface.co/docs/hub/datasets-viewer-configure). Column types come from `datasets` features. For your own Parquet files you declare them in README YAML, e.g. `dtype: image`, with image columns as struct `{bytes, path}` — [HF docs: image dataset](https://huggingface.co/docs/hub/datasets-image)
- HF conversion: "every dataset hosted in the Hub is automatically converted to Parquet format up to 5GB". For video, "the URLs to the videos are stored in the converted Parquet data without the video bytes" — [HF docs: video dataset](https://huggingface.co/docs/hub/main/datasets-video). Non-Parquet datasets over 5 GB get a partial viewer; Parquet datasets show fully but sort/filter/search only on the first 5 GB; the biggest unconverted ones get a 100-row preview — [HF docs: Data Studio](https://huggingface.co/docs/hub/data-studio). Partial conversions go in a "partial-train" split directory, and shards are about 500 MB — [HF dataset-viewer docs](https://huggingface.co/docs/dataset-viewer/parquet). A `parquet-converter` bot opens a discussion on the repo — [HF docs: Data Studio](https://huggingface.co/docs/hub/data-studio)
- HF Data Studio (2026) also has an agent-trace viewer for raw JSONL traces from Claude Code/Codex/Pi, which is a specialised renderer chosen by content rather than extension — [HF docs: Data Studio](https://huggingface.co/docs/hub/data-studio)
- HF lets authors opt out with `viewer: false` — [HF docs: configure viewer](https://huggingface.co/docs/hub/datasets-viewer-configure). Formats documented in 2025-26 include video (MP4, MOV, AVI) — [HF docs: video](https://huggingface.co/docs/hub/main/datasets-video), and NIfTI via a `Nifti` feature — [HF docs: NIfTI](https://huggingface.co/docs/datasets/nifti_dataset)
- Oxen datasets: a cell holds a relative path, and the renderer is chosen per column (`image`, `link`, `markdown`, `code`, and video in the editor). The choice is saved as schema metadata (`{"_oxen":{"render":{"func":"image"}}}`) committed to the repo — [Oxen docs: datasets](https://docs.oxen.ai/examples/data/datasets); [Oxen docs: file metadata](https://docs.oxen.ai/concepts/file_metadata); [Oxen docs: video generation](https://docs.oxen.ai/examples/fine-tuning/video_generation)
- W&B Tables cells can be scalars, arrays, or "most subclasses of `wandb.data_types.Media`" (Image, Video, Audio, …) — [W&B docs: Table](https://docs.wandb.ai/models/ref/python/data-types/table). Conversion happens at log time: arrays become PNG via Pillow, video arrays are encoded as gif/mp4/webm/ogg (needs FFmpeg/MoviePy, default 4 fps), and `Object3D` point clouds render up to 300,000 points — [CoreWeave/W&B docs: log media](https://docs.coreweave.com/products/wandb/track/log/media)
- W&B reference artifacts (files left in your bucket): one statement says "the UI cannot render rich media such as images, audio, because the data itself is not contained within the artifact". The same page also says rich media "may fail to render… depending on the CORS configuration" and that allowlisting `app.wandb.ai` fixes it — [W&B docs: external files](https://docs.wandb.ai/models/artifacts/track-external-files). **These conflict.** A likely reading is that the artifact file browser doesn't render referenced media, while Tables that point to bucket media can render with CORS set up. This is unconfirmed.
- DagsHub's Dataset Viewer overlays Label Studio-format annotations (labels, boxes, keypoints), with colour by field, class or instance — [DagsHub docs: visualizing](https://dagshub.com/docs/use_cases/data_engine/visualizing_datasets/). It can also hand off to a local FiftyOne instance — [DagsHub docs: annotation](https://dagshub.com/docs/use_cases/annotation/)
- FiftyOne picks the viewer by sample/slice `media_type` (image, video, 3d via `.fo3d` scenes holding `.pcd` point clouds) — [FiftyOne docs: groups](https://docs.voxel51.com/user_guide/groups.html)
- Encord: DICOM needs certain tags just to import, and more tags (ImagePositionPatient, ImageOrientationPatient, SliceThickness, PixelSpacing) to render in 3D — [Encord docs: Index basics](https://docs.encord.com/platform-documentation/Curate/index-files)

### Inferences
- Even the most "untyped" repos still dispatch renderers by type. They just do it per file or column instead of per container. That's the GitHub pattern and it works across mixed folders, but every renderer has hard size/format limits and a raw fallback.
- When files need conversion, viewers either convert in the background into a parallel derived artifact (HF's `refs/convert/parquet`) or convert at ingest (W&B). Both keep the original untouched and render a derivative, which fits a Sources → derived-view model.

### Gaps
- I didn't confirm the full current list of HF viewer feature types (e.g. PDF, 3D) from a primary page. A search summary claimed PDF support, but the primary pages I read only cover image, video, audio-in-general and NIfTI.
- How DagsHub picks a renderer per file type (audio/video/text) in its dataset viewer isn't documented in the pages read.

## 6. Explicit design writing on typed vs untyped containers

### Takeaway
I found no dedicated RFC or design essay comparing the two. Each side's reasoning shows up indirectly. Untyped: lakeFS (version everything together, labelling tools miss related files) and DataChain (folders aren't datasets; type the records). Typed: Labelbox (media type gates tools and validation) and Roboflow (project type gates data structure and model architectures). FiftyOne and Encord are the middle ground: groups or data groups with typed slots.

### Cited Findings
- lakeFS, "Versioning Data Labels: Integrating Labeling Tools with lakeFS" (Sep 10, 2025): labelling tools "typically lack built-in dataset versioning"; lakeFS "treats the data lake holistically… crucial for heterogeneous data scenarios" — [lakeFS blog](https://lakefs.io/blog/integrating-labeling-tools/)
- DataChain launch: "It is no longer enough to designate and version a file folder as a dataset" — [DataChain blog](https://www.datachain.ai/blog/datachain-release). DataChain + DVC example: indexing into `dataset.parquet` "saves tons of time by avoiding reading files and calculating hashes" and avoids materialising files — [example-datachain-dvc](https://github.com/shcheklein/example-datachain-dvc)
- XetHub/HF rationale on storage, not typing: Git LFS "was just never meant for the type of large files we handle in AI"; Hub stats at the time were 450k dataset repos and 12 PB in LFS (Aug 2024) — [HF blog](https://huggingface.co/blog/xethub-joins-hf)
- Labelbox: media type "is a critical step. The media type determines which annotation tools… will be available" — [Labelbox: ontologies](https://docs.labelbox.com/horizon/guides/labelbox-ontology)
- Roboflow: project type "determines how your data is structured and which model architectures you can train" — [Roboflow docs](https://docs.roboflow.com/workspaces/key-concepts)
- Encord on folder-coupling: "Mirrored datasets simplify setup at the cost of flexibility. If you need more control… use a standard folder and Dataset instead" — [Encord docs: datasets](https://docs.encord.com/platform-documentation/Annotate/annotate-datasets/annotate-datasets)
- FiftyOne: groups exist so "multiple perspectives of the same scene can be stored, visualized, and queried in ways that respect the relationships between the slices" — [FiftyOne docs: groups](https://docs.voxel51.com/user_guide/groups.html)

### Inferences
- The surveyed tools suggest a pattern for the product decision: keep Sources and Datasets untyped (a per-file renderer, like GitHub or HF). Let one Studio span a mixed folder only if a "sample" is an explicit typed composite (FiftyOne groups, Encord data groups) with one ontology. Otherwise type each Studio by modality/task (Labelbox, Roboflow, Azure, Vertex), with many Studios able to draw from the same untyped source by query (Labelbox Catalog → batch, DagsHub datasource → annotate).
- The hyperscaler typed-labelling services that were most rigid (Ground Truth frozen, Azure ML labelling retired Sept 2026) are not being invested in. This says more about market position than about typing, but it means none of the actively developed products use "container typed at the storage layer."

### Gaps
- No primary-source design rationale from Hugging Face, DagsHub or Oxen explains why their viewers dispatch per column rather than per repo.
- No public user research or metrics comparing one mixed Studio against Studios split by type.
