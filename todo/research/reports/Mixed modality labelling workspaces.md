# Type the item, not the workspace

The workspace model is sound for storage and browsing, and it's half right for labelling. Every actively developed data repository leaves the folder untyped and picks a renderer per file. That covers Hugging Face, lakeFS, DVC, Oxen, DagsHub, Labelbox Catalog and Encord's Files. Medical viewers have moved the same way. OHIF v3.13 now dispatches one study viewer to per-data-type render paths for planar images, video, ECG, whole-slide images and 3D volumes ([OHIF v3.13](https://ohif.org/release-notes/3p13/)). But "only the renderer differs per file" understates what changes between modalities. In labelling tools, the media type usually decides which annotation tools exist, which ontology vocabulary applies, how QA and consensus work, and which export formats are valid. That is why Labelbox, Scale, Kili, Supervisely, CVAT, Roboflow and most others fix one media type per project at creation and never let it change. The newest designs are Encord Data Groups (generally available in 2026), V7 slots, FiftyOne grouped datasets and OHIF modes. They keep one container, type each file or slot, and compose per-file renderers inside one task. They still run bulk operations, consensus and export over sets of a single type. For the product, this means one Studio per data kind was the wrong split: one drop of 35 files should not have produced seven Studios. The right split is one Studio per labelling *task*. Each item carries its own detected kind, renderers are chosen per item from a registry, the label schema states which kinds and geometries each class applies to, and QA and export are computed over per-kind views of the mixed set. Ingest should follow the pattern the medical platforms share: detect the format from content, keep the original untouched, write a derived browser-ready copy, and show each file's state (including failures) in the file list without blocking the rest of the batch.

## Two families: eight vendors type the project, three type the file

The commercial market splits cleanly on where media type lives. In the larger family, the *work container* is typed when it's created and usually can't change afterwards. Labelbox says that after you pick a project's data type "you will only be able to attach data rows that match… you cannot select video… and then send image data rows to this project later" ([Labelbox](https://docs.labelbox.com/docs/create-a-project)). Kili warns that "asset type is a critical choice. You won't be able to change it later" ([Kili](https://docs.kili-technology.com/docs/creating-a-new-project)). Supervisely says "you can't mix multiple content types in the same project, and this setting can't be changed later" ([Supervisely](https://docs.supervisely.com/getting-started/how-to-import)). Scale ties each project to "one specific annotation use case, which is associated with a task type" ([Scale](https://scale.com/docs/key-concepts-and-definitions)). Labellerr allows "only one data type… per project" ([Labellerr](https://docs.labellerr.com/getting-started/create-project)), and Segments.ai and BasicAI type the dataset itself. Open-source labelling tools are stricter still. CVAT says "It's not allowed to mix 1D/2D/3D tasks in the same project" and enforces one video *or* many images per task in server code ([CVAT](https://docs.cvat.ai/docs/workspace/projects/); [task.py](https://github.com/opencv/cvat/blob/develop/cvat/apps/engine/task.py)). Roboflow's project type "is cemented when you create the project" ([Roboflow forum](https://discuss.roboflow.com/t/does-project-type-matter/131)). In doccano, each project's type fixes both its interface and its output schema.

The smaller family types the *asset*. Encord projects take no media type at all: `create_project(project_title, dataset_hashes, ontology_hash, workflow_template_hash)`. Its datasets hold "a video, a single image, an image group, or a DICOM series", and the editor follows each data unit, so DICOM and NIfTI open in the DICOM editor ([Encord SDK](https://docs.encord.com/sdk-documentation/getting-started-sdk/sdk-get-started-project); [Encord entities](https://docs.encord.com/sdk-documentation/general-sdk/general-concepts-sdk); [Encord DICOM](https://docs.encord.com/platform-documentation/Annotate/annotate-label-editor/annotate-dicom)). V7 sets `type: image | video | pdf | dicom` per item or slot, inferring it from the extension when omitted ([V7](https://docs.v7labs.com/docs/registering-items-from-external-storage)). Dataloop picks the default annotation studio by file type: images open the Image Studio, PCD files the Lidar Studio, and so on ([Dataloop](https://docs.dataloop.ai/docs/annotation-studios)). Medical platforms sit almost entirely in this family. Flywheel's strict hierarchy (Project › Subject › Session › Acquisition › Files) puts modality on the leaf, and it runs "multiple protocols… in a single project… without the need to copy data to new projects" ([Flywheel hierarchy](https://docs.flywheel.io/user/navigate/user_the_flywheel_hierarchy/); [Flywheel tasks](https://docs.flywheel.io/user/workflow/tasks/user_introduction_to_read_tasks/)). MD.ai, XNAT and RedBrick likewise hold many modalities in one project. RedBrick says a task "can consist of anything - a single image, series, or entire study" ([RedBrick](https://app.redbrickai.com/docs/projects/tasks-and-assignment)).

| Layer | Typed in practice | Untyped in practice |
|---|---|---|
| Raw store / catalog | Nobody (Vertex AI datasets are typed; Ground Truth is frozen; Azure ML labelling is retired) | HF Hub, lakeFS, DVC, Oxen, DagsHub, Labelbox Catalog, Encord Files |
| Labelling project | Labelbox, Scale, Kili, Supervisely, SuperAnnotate, Labellerr, CVAT, Roboflow, doccano | Encord, V7, Dataloop, Flywheel, MD.ai, RedBrick, XNAT |
| Item / slot / series | Everyone: renderer dispatch always keys on it | Nobody |

The row that matters most is the last one. Even the most "untyped" repositories dispatch renderers by type, just per file or per column instead of per container. Oxen detects a type per file from its extension ([Oxen](https://docs.oxen.ai/concepts/file_metadata)). The Hugging Face Dataset Viewer dispatches cell renderers on each column's feature type (`Image`, `Audio`, `Video`, `Pdf`, `Nifti`) ([dataset-viewer source](https://github.com/huggingface/dataset-viewer/blob/main/libs/libcommon/src/libcommon/viewer_utils/features.py)). FiftyOne infers `media_type` per sample from MIME type or extension ([FiftyOne](https://docs.voxel51.com/user_guide/using_datasets.html)). The storage layer has also lost its typed holdouts. AWS SageMaker Ground Truth "is no longer open to new customers" ([AWS](https://docs.aws.amazon.com/sagemaker/latest/dg/sms-task-types.html)), and Azure ML data labelling retired on September 30, 2026 ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/machine-learning/how-to-create-text-labeling-projects?view=azureml-api-2)). So the product's Sources-and-Datasets-as-folders model matches what everyone does. The open question is only the Studio.

## What breaks when kinds mix is tools, ontology, QA and export, not rendering

The one reason vendors give for typing projects is tooling. Labelbox calls the ontology's media type "a critical step. The media type determines which annotation tools… will be available" ([Labelbox ontologies](https://docs.labelbox.com/horizon/guides/labelbox-ontology)). Roboflow says the project type "determines how your data is structured and which model architectures you can train", and exporters appear only for compatible types ([Roboflow](https://docs.roboflow.com/workspaces/key-concepts); [forum](https://discuss.roboflow.com/t/exporting-for-yolov8-check-your-project-type/1754)). Dataloop's tool matrix shows the same thing from the other side: 3D cuboids exist only in the LiDAR studio, and bounding boxes don't exist in the Audio or Text studios ([Dataloop](https://docs.dataloop.ai/docs/annotation-studio-basics)). No vendor gave a rationale beyond this. I found no RFC, design post or reversal post-mortem in any of the four research areas. The "why" is inferred from feature constraints, not stated.

QA is where mixing hurts most in practice. Encord, the platform that goes furthest toward mixed projects, still does not support its consensus "Determine" nodes on Data Groups ([Encord](https://docs.encord.com/platform-documentation/Curate/data-groups/index-data-groups)). Prodigy's review recipe won't handle `image_manual` or `audio_manual` because drawn shapes "vary by small pixel differences and are hard to merge" ([Prodigy](https://prodi.gy/docs/review)). CVAT branches its validation and ground-truth code on `MediaType.AUDIO` and `POINT_CLOUD`, and its segment-overlap merge "only works for bounding boxes" ([task.py](https://github.com/opencv/cvat/blob/develop/cvat/apps/engine/task.py); [CVAT tasks](https://docs.cvat.ai/docs/workspace/tasks-page/)). FiftyOne lets a grouped dataset mix images, video and 3D, but "strictly enforces that each slice… must have a homogeneous media type". Iteration, filtering and aggregation act on one active slice unless you flatten slices explicitly, and flattening slices of different media types needs a private `_allow_mixed=True` flag ([FiftyOne groups](https://docs.voxel51.com/user_guide/groups.html); [PR #4101](https://github.com/voxel51/fiftyone/pull/4101)). The lesson is not that QA forbids mixing. It is that **agreement metrics, review rules and throughput are defined per geometry and per kind**, so they have to run over views of a single kind.

The unit of work is the other real constraint. A practitioner who split a robotics episode into three Label Studio projects blamed the tool for allowing only one data item per task. The official Video + Audio + TimeSeries template contradicts that claim ([blog](https://jackpan.me/posts/three-label-studio-projects/); [LS template](https://labelstud.io/templates/timeseries_audio_video)). The point that survives is that a task per video and a task per sampled frame can't share one task list. CVAT's maintainer puts it as "Use projects to aggregate your data around the same annotations spec. Create a task when you want to annotate more data" ([cvat#9758](https://github.com/cvat-ai/cvat/issues/9758)). Label schemas also resist change once work has started. Label Studio won't let you remove labels or change the labelling type without deleting the affected annotations ([LS setup](https://labelstud.io/guide/setup)). Prodigy's maintainers recommend separate passes and datasets per annotation type rather than one combined interface ([Prodigy support](https://support.prodi.gy/t/multiple-annotation-types-on-the-same-data/3031)).

Read together, the evidence says modality matters to the *question being asked* (which classes, which geometries, which reviewer) far more than to the container. Medical platforms show the split that works: Flywheel runs several read protocols in parallel over one project, and Ango routes `.dcm` and `.nii` files to different editors with different tools while keeping them in one project ([Flywheel](https://docs.flywheel.io/user/workflow/tasks/user_introduction_to_read_tasks/); [Ango](https://docs.imerit.net/labeling/labeling-editor-interface/medical-labeling-editor)). The reasons left for hard splits are a legacy viewer that can't render a format, the regulatory clearance scope of clinical pathology viewers, and reader specialty. Flywheel's DICOM-only V3 viewer sits beside a V2 viewer kept for NIfTI and TIFF ([Flywheel viewer](https://docs.flywheel.io/user/viewer/)). FDA-cleared AISight Dx and Concentriq list specific scanner and format pairs ([K243391](https://fda.innolitics.com/submissions/PA/subpart-d%E2%80%94pathology-instrumentation-and-accessories/QKQ/K243391); [K261380](https://www.accessdata.fda.gov/cdrh_docs/reviews/K261380.pdf)). None of these needs a separate Studio per data type. They need a renderer per kind, a schema scoped per task, and reader assignment.

## Grouped items, not separate Studios, solve the patient-with-MRI-and-ECG case

When one sample spans several files, every platform that handles it well has made the *group* a typed object with typed slots, each rendered by its own viewer. Encord Data Groups "can include any data type (images, videos, audio files, text files, PDFs, DICOM series)". They use grid, carousel or custom split-pane layouts of up to 50 data units, with cross-tile object instances, one synchronised timeline and group-level classifications ([Encord Data Groups](https://docs.encord.com/platform-documentation/Curate/data-groups/index-data-groups); [Encord editor](https://docs.encord.com/platform-documentation/Annotate/annotate-label-editor/multimodal-groups)). Encord's own description frames Data Groups as a generalisation of its older image-only groups. **Auto Data Groups** (GA April 24, 2026) build groups by key from a source folder without SDK scripts, and time series became GA on October 16, 2026 as a standalone unit, a Data Group member or part of a Scene ([Encord 2026 notes](https://docs.encord.com/release-notes/releasenotes-2026)). Encord also dropped its project-level study-classification setting: study-level labels now come from grouping a study's series ([Encord DICOM](https://docs.encord.com/platform-documentation/Annotate/annotate-label-editor/annotate-dicom)). V7 puts different file types in different slots of one item and pitches this for mammography hanging protocols and ultrasound-plus-PDF records ([V7 slots](https://www.v7darwin.com/academy/slots)). FiftyOne's KITTI example has slots `{'left': 'image', 'right': 'image', 'pcd': '3d'}`. Its modal shows image and video slices in a carousel and 3D slices in a side viewer, and a shared `Instance` links the same object across slices ([FiftyOne groups](https://docs.voxel51.com/user_guide/groups.html)).

OHIF has the most mature split of responsibilities, and it maps almost one-to-one onto the product's extension host. SOP class handlers decide what an item is and turn instances into display sets. Instances no handler matches "are NOT added to any display set and will not be displayed" ([OHIF DisplaySetService](https://docs.ohif.org/llm/platform/services/data/DisplaySetService.md)). Hanging protocols score display sets against weighted rules on attributes such as `Modality` and `SeriesDescription`, and "the displaySet with the highest score will be used" ([OHIF hanging protocols](https://docs.ohif.org/llm/platform/extensions/modules/hpModule.md)). Modes declare the tools, panels and viewports. A specialised mode such as microscopy can replace a single viewport without forking the shell ([OHIF viewport](https://docs.ohif.org/llm/platform/extensions/modules/viewport.md)). RedBrick lets each project supply a hanging-protocol script that receives `Series{is2DImage, isVideo, numFrames, imagingAxis}` and returns tabs and views ([RedBrick](https://app.redbrickai.com/docs/project-pages/settings-page/custom-hanging-protocol)). The gap is visible where this is missing. CVAT's request for hanging protocols so a patient's images and videos can be shown together has been open since 2022, and today it means "opening multiple browsers" ([cvat#4648](https://github.com/cvat-ai/cvat/issues/4648)). A product that boots seven Studios for one patient drop has recreated that problem.

Two limits deserve honesty. Grouped items still constrain which tools work across tiles: Encord's shared-label-layer "Multi-Layer Data Groups" "support images only" with equal aspect ratios, and 3D tiles ignore synchronised zoom ([Encord SDK](https://docs.encord.com/sdk-documentation/index-sdk/sdk-data-groups); [Encord editor](https://docs.encord.com/platform-documentation/Annotate/annotate-label-editor/multimodal-groups)). Ango makes reference volumes view-only, and "only the main volume can be annotated" ([Ango](https://docs.imerit.net/labeling/labeling-editor-interface/medical-labeling-editor)). Also, no surveyed product offers a queue of *heterogeneous single files* in one UI, such as an image task followed by an audio task. Mixed queues exist only where every task is the same multi-file composite. Encord's one documented mixed image-and-video project ("The Ontology is the same for ALL tasks") is the closest counterexample ([Encord](https://docs.encord.com/end-to-end/Modalities/images-videos/data-import-basic-local-images-videos)). Encord's docs also don't say what happens when an ontology class can't apply to a data unit. A mixed Studio is therefore at the frontier, not off the map. Its rules for tool applicability have to be designed explicitly, because no precedent defines them.

## Convert on ingest, keep the original, and show each file's state

Whatever the browser can't decode gets converted on the server into a sibling copy. The platforms differ in how eagerly they do it and how loudly they report it. **Video** has settled on H.264 MP4 at a constant frame rate with faststart. Encord checks every uploaded video, flags problems with a red badge and a count, and on Enterprise writes a new `<name>_normalized.mp4`. It recommends `ffmpeg … -r 30 -c:v libx264 -movflags faststart` because "browsers require a constant frame rate" ([Encord re-encoding](https://docs.encord.com/platform-documentation/Curate/files/files-re-encoding); [Encord supported data](https://docs.encord.com/platform-documentation/General/general-supported-data)). CVAT accepts anything ffmpeg reads, including AVI, and stores both original and compressed chunks ([CVAT](https://docs.cvat.ai/docs/getting_started/overview/)). Ango refuses frame-specific labels on variable-frame-rate video ([Ango](https://docs.imerit.net/data/data-in-ango-hub/supported-asset-file-types)). Labelbox and FiftyOne push the transcode back to the user ([Labelbox](https://docs.labelbox.com/reference/import-video-data); [FiftyOne API](https://docs.voxel51.com/api/fiftyone.utils.video.html)). For endoscopy and cine AVIs, server-side CFR transcoding on ingest is the established answer.

**Whole-slide images** are read natively when a reader exists and converted in a background job otherwise. Kitware's large_image ships one tile-source package per format (OpenSlide, Bio-Formats, DICOM, vips…). Only inputs no source reads go through a "Large Image Conversion" job that writes a pyramidal TIFF via libvips, with 256-pixel tiles and JPEG quality 90 by default ([large_image](https://girder.github.io/large_image/); [tasks](https://girder.github.io/large_image/_modules/large_image_tasks/tasks.html)). Cytomine detects format "not based on the file extension" and converts only non-native formats ([Cytomine](https://doc.cytomine.com/user-guide/storage)). V7 auto-tiles anything over 10,000 px and lists SVS and NDPI as supported ([V7](https://docs.v7labs.com/docs/supported-file-formats)). To reach DICOMweb viewers, `wsidicomizer` converts SVS and NDPI to DICOM WSI losslessly ([wsidicomizer](http://github.com/imi-bigpicture/wsidicomizer)). Orthanc's Dicomizer is fast on tiled TIFF but must re-encode proprietary formats through OpenSlide, and it needs `--force-openslide=1` or pixel spacing can come out wrong ([Orthanc WSI](https://orthanc.uclouvain.be/book/plugins/wsi.html); [forum](https://discourse.orthanc-server.org/t/issue-with-image-dimensions-after-svs-dicom-conversion-using-orthancwsidicomizer/5585)). Reader coverage has sharp edges: QuPath's Bio-Formats can't read most NDPI files on Apple silicon, and OpenSlide is limited to 2D 8-bit RGB ([QuPath formats](https://qupath.readthedocs.io/en/stable/docs/intro/formats.html)).

**DICOM series and NIfTI** split between server conversion and in-browser parsing. Flywheel chains gears on upload: a metadata importer, then a classifier, then `dcm2niix` ([Flywheel](https://docs.flywheel.io/user/compute/gears/best-practices/user_best_practices_classifying/)). Supervisely converts DICOM to NRRD on import and finds series in any directory layout ([import-dicom-volumes](https://github.com/supervisely-ecosystem/import-dicom-volumes)). VolView and RedBrick do no server conversion: they parse DICOM and NIfTI in the browser (VolView with ITK-WASM), and VolView warns that non-DICOM orientation "cannot be assured" ([VolView](https://kitware.github.io/VolView/loading_data.html); [RedBrick](https://docs.redbrickai.com/importing-data/import-cloud-data)). Series assembly is where users get hurt. V7 asks people to zip a series and rename the zip to `.dcm`, or "each slice will be uploaded as an individual image". It orders slices by SeriesNumber, then InstanceNumber, then SliceLocation, then ImagePositionPatient ([V7 DICOM](https://docs.v7labs.com/docs/annotate-dicom-nifti-files); [V7 registration](https://docs.v7labs.com/docs/registering-items-from-external-storage)). Encord requires StudyInstanceUID, SeriesInstanceUID, SOPInstanceUID and PatientID to import, plus ImagePositionPatient, ImageOrientationPatient, SliceThickness and PixelSpacing to render in 3D ([Encord](https://docs.encord.com/platform-documentation/Curate/add-files/index-upload-local-data)). A product that classifies by content should group by SeriesInstanceUID automatically rather than rely on folder conventions.

**ECG is the unsolved one.** No labelling vendor documents native WFDB or EDF ingest. OHIF's new ECG viewport takes DICOM waveforms ([OHIF v3.13](https://ohif.org/release-notes/3p13/)). Encord takes only CSV time series, which its editor parses on open ([Encord](https://docs.encord.com/platform-documentation/Curate/add-files/index-register-cloud-data)). PhysioNet's LightWAVE reads WFDB records through a server-side C CGI, but its repository hasn't been pushed since July 2023 ([LightWAVE](https://physionet.org/static/lightwave/doc/about.html); [GitHub](https://github.com/bemoody/lightwave)). Accepting `.hea` + `.dat` pairs directly would set the product apart. It also means building the multi-file record grouping and the parser yourself.

**Progress and failures** are reported as a per-file state machine in the file list, never as one modal progress bar. Cytomine shows UPLOADED → DETECTING FORMAT → EXTRACTING DATA → CONVERTING → DEPLOYING → DEPLOYED, with a separate ERROR_FORMAT, ERROR_EXTRACTION, ERROR_CONVERSION or ERROR_DEPLOYMENT status, and failed uploads stay in storage ([Cytomine](https://doc.cytomine.com/user-guide/storage)). Aiforia exposes a numeric ConversionStatus (Uploaded, Processing, Done, Error…) that clients poll, or an `upload_complete` webhook ([Aiforia](https://cloud.aiforia.com/api/docs/integrations/scanner-integration)). Ango keeps a failed asset in place with "Preprocess failed" and creates no task for it. It retries transient errors automatically and offers bulk "Retry Preprocess", while permanent errors have no retry button ([Ango](https://docs.imerit.net/data/importing-assets/bundled-assets/importing-multiple-single-frame-dicom-files-as-a-3d-dicom-series)). Proscia added "re-ingest failed images directly from the Image Management worklist" in 2026, and Orthanc's Education plugin shows the Dicomizer's logs on its upload page ([Proscia](https://tissuepathology.com/2026/02/12/proscia-new-in-concentriq-ap-smoother-review-and-enhanced-performance/); [Orthanc Education](https://orthanc.uclouvain.be/book/plugins/education.html)). Silent reshaping is the anti-pattern: V7's `series` merge mode simply ignores other file types ([V7 upload](https://docs.v7labs.com/docs/upload-images)), and MD.ai turns every file without its folder convention into a separate study ([MD.ai](https://docs.md.ai/annotator/datasets/create-dataset/)). Converter packaging follows native dependencies. Flywheel runs one Docker image per gear, Cytomine PIMS has ordered format plugins, and large_image keeps heavy readers as optional extras ([dcm2niix gear](https://github.com/flywheel-apps/dcm2niix); [PIMS](https://github.com/cytomine/pims); [large_image setup](https://github.com/girder/large_image/blob/master/setup.py)).

## Recommendation: one Studio per task over mixed, typed items

**Data model.** Keep Sources and Datasets untyped. A Source is a folder of immutable originals. A Dataset is a curated table of item references, and its collections are organisational (split, cohort, patient, site), not one per kind. Type the *item*. Each file gets a content-detected `kind` and one or more derived representations (original, browser-ready, thumbnail). Multi-file samples become first-class *group items* with named, typed slots and a primary slot. Examples are a DICOM series, a WFDB `.hea`+`.dat` record, or a patient with MRI + ECG + report. Collection-per-kind can remain as a saved filter or facet, because Encord and FiftyOne both filter by media type for curation ([Encord explore](https://docs.encord.com/platform-documentation/Curate/index-video)). It should not be a storage boundary.

**Unit of work.** The Studio should be scoped by *task*, a labelling question with its label schema, workflow and assignees, as in Encord (dataset + one ontology + workflow), Flywheel (protocol over a project) and CVAT ("same annotations spec"). Within a task, the unit of work is the item, a single file or a group. A task declares the set of kinds it *accepts* as a filter, not one required kind. "Segment the left ventricle" accepts volumes and 4D cine. "Is this study adequate for diagnosis?" accepts everything. A drop should therefore create one draft dataset and *one* Studio by default: a triage or review task over the whole mixed set, where each item opens in its own renderer. Specialised tasks are suggested and created only when someone defines a question, never one per detected kind. The 35-file drop then produces one Studio, and seven only if seven real tasks exist.

**Renderer choice.** Drop "an environment extends one preset with one data kind and one renderer". Move to OHIF's three-part split. First, kind detectors, like SOP class handlers: every item gets a kind, or an explicit "attachment" fallback in the spirit of XNAT Resources ([XNAT](https://wiki.xnat.org/documentation/adding-or-removing-resource-files)), so nothing vanishes. Second, a renderer registry keyed by kind, with optional scoring for overrides. The environment holds a *map* from kind to renderer and config rather than a single renderer. Third, layouts that act as hanging protocols for group items. Tools available on an item should be computed as the intersection of what its renderer supports and what geometries the schema declares, so an inapplicable tool is never offered. That fills the gap Encord leaves undocumented.

**Label schemas and QA.** Use one schema per task. Each class declares the geometries and kinds it applies to, and item- or group-level classifications are valid on any kind. This mirrors Encord's shared ontology and BasicAI's split of general and sensor-specific attributes ([BasicAI](https://docs.basic.ai/docs/attribute-classification)). Don't type the schema by media type the way Labelbox does. That choice forces a schema per kind, and a project per kind follows from it. Run QA over single-kind views of the mixed task: agreement, consensus and review-rule thresholds per kind and geometry, and throughput reported per kind (frames, slices and items are not comparable). Make exporters kind-aware, so one task can export COCO for its images and NIfTI or DICOM SEG for its volumes. Treat changing a schema mid-task as a versioned migration, because every tool that allows edits later restricts them once annotations exist.

**Ingest and conversion.** Sniff content, not extensions, and assemble DICOM series by SeriesInstanceUID and WFDB records by basename at classification time. Keep originals immutable in Sources. Write derived copies next to them, the way Encord writes `_normalized` files and Hugging Face keeps a parallel Parquet branch ([HF](https://huggingface.co/docs/dataset-viewer/parquet)): H.264 CFR faststart MP4 for AVI and other video, a pyramidal tiled image (with DICOM WSI as an optional export) for SVS and NDPI, an assembled, ordered volume with required-tag validation for DICOM, and a parsed signal representation for WFDB. NIfTI and small DICOM can be parsed client-side, as VolView does. Give every file a visible state (stored, detecting, converting, ready, failed with a reason, unsupported). Separate transient from permanent errors, retry transient ones automatically, allow bulk retry, and never block the batch. Package converters as one worker image per native-dependency family: ffmpeg for video, OpenSlide and libvips for WSI, DICOM and volume tools, and a waveform parser. Each is registered against the kinds it accepts, like Flywheel's gear rules.

## Conclusion

The research reframes the question. "One Studio versus seven Studios" is the wrong axis. Modality and task are independent, and the current product joins them, so a single question ("triage this drop") becomes seven Studios. At the same time, a real need ("segment volumes and grade slides in one project") gets no clean home. Typed-project vendors made the same join, and Labelbox's retreat from DICOM ([Labelbox deprecations](https://docs.labelbox.com/horizon/guides/deprecations)) shows the cost: each modality becomes a separate product surface that has to earn its usage. The platforms gaining ground in medical work (Encord, V7, Flywheel, OHIF) separated the two, typing items and scoping work by question.

The hard part of a single mixed Studio is not rendering, which the extension host already does per plugin. It is designing three rules no vendor has fully published: which tools apply to which item, how consensus is computed when items differ in kind, and how one schema covers several geometries. If the product makes those rules explicit, it is ahead of the market rather than behind it. Native WFDB ingest is the clearest place to be first, because nobody else documents it.
