# How open-source and developer-oriented labelling and dataset tools organise mixed data types (2026)

Scope: Label Studio, CVAT, FiftyOne, Roboflow, Prodigy, doccano, MONAI Label + 3D Slicer, QuPath, OHIF Viewer, napari, Argilla, Hugging Face datasets and the Dataset Viewer. Research date: 2 Nov 2026. Sources are current docs or source code unless flagged. Secondary sources (DeepWiki, personal blogs, wiki aggregators) are marked as such.

## Q1. Where does "media type" live: project, dataset, task, sample, or file?

### Takeaway
There are three patterns. In the first, the project type fixes the editor: CVAT, Roboflow, doccano and Prodigy (per recipe and session). In the second, the editor is composed from a per-project schema of typed fields: Label Studio, Argilla and Hugging Face datasets. In the third, the media type is inferred per file or sample and the viewer is chosen at render time: FiftyOne (per sample, but the dataset must be homogeneous unless it is grouped), OHIF (per series, through the SOP Class handler and hanging protocol), napari (per file, through the reader plugin) and QuPath (per image, through the image server). No tool in scope stores a free-form media type per file inside one project and swaps the full editor for each file in a heterogeneous list. FiftyOne grouped datasets and OHIF come closest.

### Cited Findings

**Label Studio: the media type is in the project's labelling config, as typed object tags bound to task data keys.**
- All labelling happens inside a project. The project has one XML labelling configuration made of Object tags (the data type and its source), Control tags (the annotation type) and Visual tags (layout) — [Label Studio: Configure labeling interface](https://labelstud.io/guide/setup)
- Object tags read values from the task's `data` dictionary through `$key` references (e.g. `<Image value="$image_url"/>`). Each task's `data` keys must match the source keys the config expects — [Label Studio: setup](https://labelstud.io/guide/setup); [Label Studio: Import data](https://labelstud.io/guide/tasks.html)
- One config can combine several object tags. The official "Time Series + Audio + Video" template syncs `<Video>`, `<Audio>` and `<TimeSeries>` through a shared `sync="group_a"` attribute, and the docs warn that `frameRate` must be set on the video or the synchronisation will be wrong — [Label Studio template: timeseries_audio_video](https://labelstud.io/templates/timeseries_audio_video)
- The import docs list "Tasks with multiple data types" (.csv/.tsv/.json/.jsonl/.parquet) as a format of its own. To label multiple data types together you must use Label Studio JSON format — [Label Studio: Import data](https://labelstud.io/guide/tasks.html)
- The YOLO ML backend docs say: "You can mix different object and control tags in one project" — [Label Studio: YOLO ML backend](https://labelstud.io/guide/ml_tutorials/yolo.html)
- Changing the config of a project with work in progress is restricted. You cannot remove labels or change the type of labelling unless you delete the annotations that use them, and Data Manager tabs are removed when the config changes — [Label Studio: setup](https://labelstud.io/guide/setup)

**CVAT: media type is fixed per task (one data type). The project fixes the dimension (1D/2D/3D) and the label set.**
- Hierarchy is Project → Task → Job, and annotation always happens at job level — [CVAT Academy overview](https://www.cvat.ai/academy/cvat-overview)
- "You can create a project containing tasks of the same type. All tasks related to the project will inherit a list of labels." The projects page also states: "It's not allowed to mix 1D/2D/3D tasks in the same project." — [CVAT docs: Projects](https://docs.cvat.ai/docs/workspace/projects/)
- "You can't mix 2D and 3D data in the same task" (3D tasks take .pcd/.bin archives plus related images) — [CVAT docs: Tasks](https://docs.cvat.ai/docs/workspace/tasks-page/)
- The server enforces one data kind per task. `task.py` raises `"Only one {unique types} or many {multiple types} can be used simultaneously"`, so a task holds either one video or many images. It also detects `media_type` (IMAGE, AUDIO, POINT_CLOUD) and `dimension` (1D/2D/3D) per task and switches the chunk type on `(media_type, mode)` — [cvat/apps/engine/task.py](https://github.com/opencv/cvat/blob/develop/cvat/apps/engine/task.py)
- Supported input: images (any format Pillow reads), video (any format ffmpeg reads, e.g. MP4/AVI/MOV), audio (WAV/MP3/FLAC/OPUS) and 3D (.pcd, .bin) — [CVAT Overview](https://docs.cvat.ai/docs/getting_started/overview/)
- Vocabulary: "2D" tasks are images and videos, "3D" tasks are point clouds — [CVAT Vocabulary](https://docs.cvat.ai/docs/getting_started/vocabulary/)
- A maintainer (bsekachev, Aug 2025) said you cannot add images to an existing task: "Use projects to aggregate your data around the same annotations spec. Create a task when you want to annotate more data." — [cvat-ai/cvat#9758](https://github.com/cvat-ai/cvat/issues/9758)

**FiftyOne: media type is inferred per sample from the file, and the dataset's media type is set by its first sample.**
- `Sample.media_type` is inferred from the MIME type or extension (`image/*` → image, `video/*` → video, `*.fo3d` → 3d, `*.pcd` → point-cloud, anything else → unknown). It can be set explicitly and is immutable — [FiftyOne: Using datasets](https://docs.voxel51.com/user_guide/using_datasets.html)
- "Datasets are homogeneous; they must contain samples of the same media type (except for grouped datasets)." Adding a video to an image dataset raises `MediaTypeError: Sample media type 'video' does not match dataset media type 'image'` — [FiftyOne: Using datasets](https://docs.voxel51.com/user_guide/using_datasets.html)
- Dataset media types are `image`, `video`, `3d`, `point-cloud`, `group`, `unknown` (fallback) and custom (introduced in FiftyOne 1.5.0 / Voxel51 Enterprise 2.8.0) — [FiftyOne: Using datasets](https://docs.voxel51.com/user_guide/using_datasets.html)
- FiftyOne 1.15.0 (1 May 2026) lets 3D datasets point directly at mesh or point-cloud files when `media_type="3d"` is declared. It also added direct support for PCD/PLY/STL/FBX/GLTF and "improved support of sparse / imbalanced group datasets" — [FiftyOne release notes 1.15.0](https://docs.dev.voxel51.com/release-notes.html)
- Voxel51's own agent skill lists `.mcap/.bag/.rrd` as a `multimodal` media type. It warns that mixing MCAP with images or videos in a non-grouped dataset raises a media-type conflict, so MCAP should go in its own dataset or group slice. This is a Voxel51 repo, but it is not the main docs — [voxel51/fiftyone-skills SKILL.md](https://github.com/voxel51/fiftyone-skills/blob/main/skills/fiftyone-dataset-import/SKILL.md)

**Roboflow: the project type (the CV task) is fixed when the project is created.**
- When you create a project you must choose one type: Object detection, Classification, Instance segmentation, Keypoint detection, Semantic segmentation or Multimodal. The type "determines how your data is structured and which model architectures you can train" — [Roboflow docs: Workspaces, Projects, and Models](https://docs.roboflow.com/workspaces/key-concepts)
- The type "is cemented when you create the project and cannot be changed later". To convert, export a version and import it into a new project of the target type — [Roboflow forum: Does project type matter? (2022–2023)](https://discuss.roboflow.com/t/does-project-type-matter/131); [Roboflow forum: changing OD → instance seg (2024)](https://discuss.roboflow.com/t/help-changing-existing-project-from-objectect-detection-to-instance-segmentation/4586)
- Export formats depend on the project type. YOLOv8 export appears only in object detection, instance segmentation or classification projects — [Roboflow forum: Exporting for YOLOv8](https://discuss.roboflow.com/t/exporting-for-yolov8-check-your-project-type/1754)
- Note: Roboflow is image-centric. Its key-concepts page describes a project as managing "Images" and annotations — [Roboflow key concepts](https://docs.roboflow.com/workspaces/key-concepts)

**Prodigy: the media type is set by the recipe (which picks the interface) for each annotation session. Datasets are named stores of annotations.**
- Each built-in recipe has a fixed interface and takes a `dataset` argument to save into. Examples: `ner.manual` uses the `ner_manual` interface, `image.manual` uses `image_manual` and loads images by default, and `audio.manual` uses `audio_manual` and takes `--loader video` for video files — [Prodigy: Built-in recipes](https://prodi.gy/docs/recipes)
- The support team recommends separate sessions per task, each saving to a different dataset, merged later by `train` / `data-to-spacy` — [Prodigy support: several tasks on the same data](https://support.prodi.gy/t/how-to-setup-prodigy-for-several-tasks-on-the-same-data-points/7168)
- You can combine interfaces (e.g. spans plus a text input), but Ines Montani wrote that transcribing and annotating entities at the same time "isn't easily possible… it's also something we wouldn't recommend" — [Prodigy support: Multiple annotation types on the same data](https://support.prodi.gy/t/multiple-annotation-types-on-the-same-data/3031)

**doccano: each project has exactly one project type, and that type fixes both the modality and the UI.**
- doccano has nine project classes: TextClassification, SequenceLabeling, Seq2seq, IntentDetectionAndSlotFilling, Speech2text, ImageClassification, BoundingBox, Segmentation, ImageCaptioning. "Each doccano project is one task type, which determines the UI and output schema." Accepted import formats depend on the project type — secondary sources: [Hivebook wiki on doccano 1.8.4](https://hivebook.wiki/wiki/doccano-open-source-text-annotation-tool); [DeepWiki: doccano project types](https://deepwiki.com/doccano/doccano/4.1-project-types-and-settings)
- Official workflow: "Set up the labeling project. Select the type of labeling project…", then import a dataset — [doccano docs/index.md](https://github.com/doccano/doccano/blob/master/docs/index.md)

**MONAI Label + 3D Slicer: the modality is set by the server "app" (radiology / pathology / endoscopy / bundle) plus the datastore. The viewer is a separate client that you pick for each app.**
- The sample apps are Radiology (3D CT/MR, used with 3D Slicer, OHIF or MITK), Pathology (WSI, used with QuPath or Digital Slide Archive), Endoscopy (video, used with CVAT) and MONAI Bundle — [MONAI Label README](https://github.com/project-monai/monailabel); [MONAI Label site](https://project-monai.github.io/label.html)
- The server starts one app against one datastore: `monailabel start_server --app radiology --studies <path or DICOMweb URL> --conf models …` — [MONAI Label: App deployment](https://docs.monai.io/projects/label/en/latest/appdeployment.html); [MONAI Label README](https://github.com/project-monai/monailabel)
- The local datastore is a folder of images (e.g. `spleen_10.nii.gz`) with labels in `labels/final`. The README calls this "Local Datastore for the Radiology App on single modality images" — [MONAI Label README](https://github.com/project-monai/monailabel)

**QuPath: a project is a list of images (typically WSIs). The reader ("image server") and image type are set per image when it is imported.**
- Projects "group together related images" and let you switch between images through thumbnails. Images are not copied: the `.qpproj` stores paths and metadata — [QuPath docs: Projects](https://qupath.readthedocs.io/en/stable/docs/tutorials/projects.html); [QuPath BCM workshop](https://montpellierressourcesimagerie.github.io/qupath-bcm-workshop/lectures/project-creation.html)
- Per-image import options: Image server (Default/auto, Bio-Formats, OpenSlide, ImageJ, JSON server), Image type (Brightfield H&E, H-DAB, fluorescence…), rotation and auto-generated pyramids — [QuPath docs: Projects](https://qupath.readthedocs.io/en/stable/docs/tutorials/projects.html); [QuPath workshop](https://montpellierressourcesimagerie.github.io/qupath-bcm-workshop/lectures/project-creation.html)

**OHIF Viewer: the media type lives per DICOM series/instance (SOP Class UID, Modality). The renderer is chosen per display set.**
- `DisplaySetService` converts instance metadata into DisplaySets using the SOPClassHandlers that the mode registers. The handlers run in order and consume instances, and "any instances not matched are NOT added to any display set and will not be displayed". One series can be split into several display sets (e.g. mammography LCC/RCC) — [OHIF: DisplaySet Service](https://docs.ohif.org/llm/platform/services/data/DisplaySetService.md)
- Which Viewport component is used "depends on: Hanging Protocols, the Layout Configuration, Registered SopClassHandlers". A mode maps viewport namespaces to the SOPClassHandler IDs they display (`displaySetsToDisplay`) — [OHIF: Viewport module](https://docs.ohif.org/llm/platform/extensions/modules/viewport.md); [OHIF: Modes](https://docs.ohif.org/platform/modes/)

**napari: there is no project. The media type is resolved per file (or list of paths) by reader plugins, which return typed layers.**
- Reader contributions declare `filename_patterns`. napari only offers a file to plugins whose patterns match, and the plugin's `get_reader` can still decline by returning `None`. The reader returns `LayerData` tuples `(data, meta, layer_type)` such as image, labels or points — [napari: Plugin contributions](https://napari.org/stable/plugins/building_a_plugin/guides.html); [npe2 manifest spec](https://hackmd.io/@napari-wg-plugin/HyJ6-OwBK)

**Argilla: the media type lives in the dataset `Settings`, as typed fields.**
- `rg.Settings(fields=[TextField, ImageField, ChatField…], questions=[…])`. Fields are what annotators see and questions collect their feedback. An `ImageField` can sit next to text fields in one dataset — [Argilla: Fields](https://docs.argilla.io/latest/reference/argilla/settings/fields/); [Argilla: rg.Settings](https://docs.argilla.io/latest/reference/argilla/settings/settings/)
- (Secondary) ChatField and ImageField arrived in 2.x. Fields appear in the UI in the order they are declared, and importing from the Hub auto-suggests a layout from the dataset's features — [codexpedite article](https://codexpedite.dev/articles/argilla-feedback-dataset-model)

**Hugging Face datasets: the media type lives per column (feature).**
- `Features` is a dict of column → type. The registered types include `Image`, `Audio`, `Video` (decoded with torchcodec), `Pdf` (pdfplumber), `Nifti` (nibabel), `Mesh`, `Array2D–5D`, `Json`… and media types load lazily with a decoder — [datasets/features/features.py](https://github.com/huggingface/datasets/blob/main/src/datasets/features/features.py)
- The Dataset Viewer chooses the cell renderer by column feature type. `get_cell_value` dispatches on `isinstance(fieldType, Image | Audio | Video | Pdf …)` and recurses into `List` — [dataset-viewer libcommon viewer_utils/features.py](https://github.com/huggingface/dataset-viewer/blob/main/libs/libcommon/src/libcommon/viewer_utils/features.py)
- The Hub's upload guide says media types such as Image(), Audio(), Video() and Pdf() "enable Dataset Viewer previews" — [HF Hub: Dataset upload decision guide](https://huggingface.co/docs/hub/en/datasets-upload-guide-llm)
- A Viewer error in the forum lists the feature types it accepts as `Value … Audio, Image, Video, Pdf, Nifti, Json`, and it rejected `Mesh`. So the Viewer's datasets version lagged behind `main`, which already has `Mesh` — [HF forum: ConfigNamesError](https://discuss.huggingface.co/t/dataset-viewer-issue-confignameserror/176738)

### Inferences
- Tools built for labelling work (CVAT, Roboflow, doccano, Prodigy) attach the media type to the unit of work (project or task) because tools, ontology and export formats depend on it. Tools built for browsing data (FiftyOne, the HF Viewer, OHIF, napari, QuPath) attach it to the file or column and choose a renderer per item.
- Label Studio sits in between. The project schema is the "studio", but one schema can declare several typed panes, so "mixed" means mixed inside a task, not a mix of tasks with different types.

### Gaps
- The doccano evidence comes from secondary sources (DeepWiki and a wiki aggregator). The official docs only say you "select the type of labeling project". I did not read `backend/projects/models.py` myself.
- I did not check whether Roboflow's "Multimodal" project type (listed in its key concepts) accepts non-image media. The docs snippet suggests it covers image + text (VLM) tasks only.

## Q2. Can a single project/dataset mix modalities, and what breaks or is limited when you do?

### Takeaway
CVAT, Roboflow and doccano forbid it outright, and CVAT even forbids 2D + 3D tasks in one project. FiftyOne forbids it in a flat dataset but allows it through group slices. Each slice stays homogeneous, filters and aggregations act on one active slice, and the 3D grid needs pre-rendered projections. Label Studio allows several modalities inside every task under one config, but not tasks that each have a different modality. Its known rough edges are rendering bugs, direct upload accepting only one data key, and configs that are hard to change later. Viewer-style tools (OHIF, QuPath, napari, HF) mix freely because they choose the renderer per item.

### Cited Findings
- **CVAT:** "It's not allowed to mix 1D/2D/3D tasks in the same project." Projects share one label list across their tasks — [CVAT: Projects](https://docs.cvat.ai/docs/workspace/projects/). Within a task you get either one video or many images, never both — [task.py](https://github.com/opencv/cvat/blob/develop/cvat/apps/engine/task.py). An image project and a video project can still share labels, because 2D covers images and video — [CVAT Vocabulary](https://docs.cvat.ai/docs/getting_started/vocabulary/)
- **CVAT feature limits by media type:** in `task.py`, validation-mode handling branches on `MediaType.AUDIO` and `MediaType.POINT_CLOUD` (separate code paths for GT/validation per media type), and chunk formats differ per media type and mode — [task.py](https://github.com/opencv/cvat/blob/develop/cvat/apps/engine/task.py). The "Sorting method" option "does not work for the video data", and overlap or merge across segments "only works for bounding boxes" — [CVAT: Tasks](https://docs.cvat.ai/docs/workspace/tasks-page/)
- **FiftyOne flat datasets** raise `MediaTypeError` on a mismatch — [FiftyOne: Using datasets](https://docs.voxel51.com/user_guide/using_datasets.html)
- **FiftyOne grouped datasets:** "Grouped datasets may contain a mix of different modalities (e.g., images, videos, and 3D scenes), but FiftyOne strictly enforces that each slice of a grouped dataset must have a homogeneous media type." All slices share one schema, so a field added on one slice is declared on all of them. Iteration, filtering and aggregations apply only to the active slice unless you use `select_group_slices()` or the `groups.<slice>.field` syntax. In the App you must populate orthographic projection images before 3D scenes show in the grid — [FiftyOne: Grouped datasets](https://docs.voxel51.com/user_guide/groups.html)
- **FiftyOne metadata schema in mixed groups:** PR #4101 fixed a bug where the `metadata` schema did not expand to include the video fields (`frame_rate`, `duration`, `encoding_str`…) when a video slice was added to a group that held images. After the fix, the field type stays the generic `Metadata`. The repro uses `select_group_slices(_allow_mixed=True)`, a private flag needed to flatten slices of different media types — [voxel51/fiftyone#4101](https://github.com/voxel51/fiftyone/pull/4101)
- **FiftyOne flattened views:** `select_group_slices("left")` returns a view with `media_type == "image"`, so any image-only operation works on it. Filters applied before `select_group_slices` are not carried over — [FiftyOne: Grouped datasets](https://docs.voxel51.com/user_guide/groups.html)
- **Label Studio (allowed in one task):** Video + Audio + TimeSeries synced — [LS template](https://labelstud.io/templates/timeseries_audio_video). Multiple data types need JSON/CSV import. Drag-and-drop upload only works when the config has one data key — [Import data](https://labelstud.io/guide/tasks.html); [HumanSignal/label-studio#6321 (community answer)](https://github.com/HumanSignal/label-studio/issues/6321)
- **Label Studio (bugs):** issue #7326 reports that Video does not render when combined with both Image and Text in one task. A commenter could not reproduce it and blamed the video file not loading in the browser — [HumanSignal/label-studio#7326](https://github.com/HumanSignal/label-studio/issues/7326)
- **Label Studio (practitioner view, secondary and partly contradicted):** a 2026 blog post argues that a task "carries exactly one piece of data". It says Video + Image + KeyPoint cannot share a task, so one robotics episode became three projects (video, ego frames, exo frames) — [Jack Pan blog](https://jackpan.me/posts/three-label-studio-projects/). This is contradicted by the official template that combines Video, Audio and TimeSeries in one task and by the docs on mixed object tags — [LS template](https://labelstud.io/templates/timeseries_audio_video); [LS YOLO docs](https://labelstud.io/guide/ml_tutorials/yolo.html). The practical point that survives is different: their units of work differ (one task per video against one task per sampled frame), so they could not share a task list.
- **Label Studio (config is per project):** removing labels or changing the labelling type requires deleting existing annotations, and config changes delete Data Manager tabs — [LS setup](https://labelstud.io/guide/setup)
- **Roboflow:** the project type is fixed and it decides which model architectures and export formats you can use — [Roboflow key concepts](https://docs.roboflow.com/workspaces/key-concepts); [forum: YOLOv8 export](https://discuss.roboflow.com/t/exporting-for-yolov8-check-your-project-type/1754)
- **Prodigy (review):** the review recipe does not support `image_manual` / `audio_manual` because drawn shapes vary by small pixel differences and are hard to merge — [Prodigy: Review](https://prodi.gy/docs/review)
- **Argilla / HF:** a dataset can mix text, image and chat fields, or image, audio and video columns. The schema is fixed per dataset, though: every record has the same fields — [Argilla Fields](https://docs.argilla.io/latest/reference/argilla/settings/fields/); [HF features.py](https://github.com/huggingface/datasets/blob/main/src/datasets/features/features.py)
- **QuPath:** a project can hold images read by different servers and of different image types (brightfield, fluorescence, multiplexed) — [QuPath: Projects](https://qupath.readthedocs.io/en/stable/docs/tutorials/projects.html); [QuPath: Formats](https://qupath.readthedocs.io/en/stable/docs/intro/formats.html). It is still a 2D, microscopy-only tool.

### Inferences
- The things that break when you mix are usually the ones scoped per project in these tools: the ontology (CVAT label lists, Roboflow classes), the toolset and keyboard shortcuts (Label Studio controls bind `toName` to a specific object tag), task-splitting and QA settings (CVAT segment, overlap and validation differ by media type), and export formats (Roboflow and CVAT exporters are per task type). Browsing, storage and versioning do not break.
- The FiftyOne approach (one container, per-item media type, renderer chosen per slice, operations run against a homogeneous view) is the clearest precedent for "one repository of folders where only the renderer differs per file". It still requires homogeneous sub-collections whenever bulk operations, metrics or export run.

### Gaps
- I found no documented per-modality QA or metrics behaviour in Label Studio for multi-object configs (e.g. agreement metrics across Image and TimeSeries regions in one task).
- I did not verify keyboard-shortcut conflicts in multi-object Label Studio configs from primary sources.

## Q3. How do grouped samples work, and how is the active renderer chosen?

### Takeaway
FiftyOne groups samples by a shared `group` id with named slices, and each slice has one media type. The App's modal shows image and video slices in a carousel and 3D slices in a side 3D visualiser, and a pin marks the active slice. OHIF groups by DICOM study/series. SOP Class handlers turn instances into display sets, and hanging protocols score display sets against selector rules (Modality, SeriesDescription…) and assign them to viewports of a given type (stack, volume, microscopy, video, SR). In both, the renderer follows the item's type and the layout is configured separately.

### Cited Findings
- **FiftyOne group construction:** create a `fo.Group()` and set `group=group.element("<slice>")` on each sample. `dataset.media_type == "group"`, `group_slices` lists the slice names and `group_media_types` maps slice → media type. Both are "dynamically expanded as you add samples" — [FiftyOne: Groups](https://docs.voxel51.com/user_guide/groups.html)
- **Default and active slice:** `default_group_slice` (inferred from the first sample if not set) controls what the API returns and what the App grid shows. `dataset.group_slice = "left"` changes the active slice for the session — [FiftyOne: Groups](https://docs.voxel51.com/user_guide/groups.html)
- **KITTI example:** `quickstart-groups` has `{'left': 'image', 'right': 'image', 'pcd': '3d'}` — [FiftyOne: Groups](https://docs.voxel51.com/user_guide/groups.html)
- **App modal:** "If the group contains image/video slices, the lefthand side of the modal will contain a scrollable carousel… If the group contains 3D slices, the righthand side of the modal will contain a 3D visualizer." Multiple PCD slices can share a world frame through static transforms. The sidebar statistics cover the focused slice (marked by a pin icon) unless you switch on `group` mode in settings. Dynamic grouping can play scenes back by `frame_number` — [FiftyOne: Groups](https://docs.voxel51.com/user_guide/groups.html)
- **Cross-slice linking:** the same `Instance` is assigned to Detections, Keypoints or Polylines across slices to mark the same physical object — [FiftyOne: Groups](https://docs.voxel51.com/user_guide/groups.html)
- **Robotics/LeRobot importer:** "Each episode is a group with camera views as slices" — [FiftyOne LeRobot importer](https://docs.voxel51.com/plugins/plugins_ecosystem/fiftyone_lerobot_importer.html)
- **OHIF hanging protocols:** a protocol defines the layout, the viewport type and orientation (stack or volume), which display sets go in which viewport, initial settings and sync groups. `displaySetSelectors` use weighted `seriesMatchingRules` on attributes such as `Modality`, `isReconstructable` and `SeriesDescription`, and "the displaySet with the highest score will be used" — [OHIF: Hanging Protocol module](https://docs.ohif.org/llm/platform/extensions/modules/hpModule.md)
- **OHIF SEG and SR protocols:** the built-in `@ohif/seg` and `@ohif/sr` protocols select `Modality == SEG` and `Modality == SR` and use `stack` viewports with `allowUnmatchedView`. The SEG protocol adds a `hydrateseg` sync group across viewports that share a Frame of Reference — [OHIF coverage: cornerstone-dicom-seg getHangingProtocolModule.ts](https://docs.ohif.org/coverage/extensions/cornerstone-dicom-seg/src/gethangingprotocolmodule.ts); [cornerstone-dicom-sr](https://docs.ohif.org/coverage/extensions/cornerstone-dicom-sr/src/gethangingprotocolmodule.ts)
- **OHIF viewport choice:** "Which Viewport component is used depends on: Hanging Protocols, The Layout Configuration, Registered SopClassHandlers". Extensions ship viewport components for 2D imaging (cornerstone), SR and encapsulated PDF — [OHIF: Viewport module](https://docs.ohif.org/llm/platform/extensions/modules/viewport.md). The dicom-video and dicom-microscopy extensions each register their own viewport (`dicom-video`, `microscopy-dicom`) and their own SOP class handlers — [dicom-video index.tsx (GitLab mirror)](https://gitlab.au.dk/klips/ohif-viewer/-/blob/master/extensions/dicom-video/src/index.tsx); [dicom-microscopy index.tsx (GitLab mirror)](https://gitlab.au.dk/klips/ohif-viewer/-/blob/master/extensions/dicom-microscopy/src/index.tsx)
- **OHIF modes:** a mode declares its extensions, layout template, side panels, viewports with `displaySetsToDisplay`, hanging protocols and `sopClassHandlers` — [OHIF: Modes](https://docs.ohif.org/platform/modes/). (Secondary) The microscopy mode is deliberately minimal (one large viewport, no MPR, no radiology measurement tools) and handles only VL Whole Slide Microscopy — [DeepWiki: OHIF Microscopy and WSI](https://deepwiki.com/OHIF/Viewers/6.6-microscopy-and-wsi)
- **CVAT has no equivalent:** issue #4648 (2022, still open, enhancement) asks for OHIF-style hanging protocols so a "group" of images and videos from one patient can be shown in a grid and annotated separately. Today that needs "opening multiple browsers to compare images/videos from different Tasks" — [cvat-ai/cvat#4648](https://github.com/cvat-ai/cvat/issues/4648). CVAT 3D tasks can include "related_images" as context images for each point cloud — [CVAT: Tasks](https://docs.cvat.ai/docs/workspace/tasks-page/)
- **Label Studio "groups":** these exist only inside one task, through several object tags in one config that share a `sync` group for time alignment — [LS template](https://labelstud.io/templates/timeseries_audio_video)

### Inferences
- OHIF's split is the most developed precedent for "one repository, a renderer per item". The SOP class handler decides what an item is and which viewport can render it. The hanging protocol decides the layout. The mode decides which tools and panels exist. In OHIF the specialised workflow (e.g. microscopy) is a separate mode, so it acts as a per-data-type "studio", but it runs over the same study list and data source.
- The FiftyOne App takes a similar line without modes: one App, with the renderer picked per slice media type inside a shared modal.

### Gaps
- I could not confirm from the primary OHIF docs how a mode declares which modalities it is valid for (e.g. `isValidMode` checking the study's modalities), or how the worklist offers modes for each study. My understanding is that this exists, but I did not fetch the source, so treat it as unverified.
- The DeepWiki claim that dicom-microscopy-viewer renders with VTK.js is unverified, and it may be wrong (I believe it uses OpenLayers). Verify before citing.

## Q4. How do they handle formats that need conversion on ingest?

### Takeaway
Most tools leave conversion to the user or do it in server-side Python with ffmpeg. FiftyOne asks the user to run `reencode_videos()` (ffmpeg → H.264 MP4). CVAT's server decodes any format ffmpeg reads into chunks (video segments or zipped frames). Label Studio accepts only browser-playable mp4 and webm. QuPath reads WSIs locally through OpenSlide or Bio-Formats and builds pyramids on the fly for large flat images. OHIF needs DICOM over DICOMweb, so you convert proprietary WSIs to DICOM first (wsidicomizer) and NIfTI to DICOM (e.g. plastimatch). HF decodes lazily with torchcodec and nibabel.

### Cited Findings
- **FiftyOne video:** the App uses HTML5 `<video>` and plays whatever the browser can (MP4/H.264, WebM, Ogg). For an unsupported codec it prompts you to run `fiftyone.utils.video.reencode_videos()` — [FiftyOne FAQ](https://docs.voxel51.com/faq/). The default command is `ffmpeg -c:v libx264 -preset medium -crf 23 -pix_fmt yuv420p -an`, with options to update paths in place or write elsewhere, and metadata is not refreshed automatically — [fiftyone.utils.video API](https://docs.voxel51.com/api/fiftyone.utils.video.html). A maintainer (brimoor) said the re-encode helpers hard-code H.264 MP4 "as that is a common codec that all browsers support" — [voxel51/fiftyone#4124 (2024)](https://github.com/voxel51/fiftyone/issues/4124). The zoo UCF101 recipe re-encodes as a required step — [FiftyOne UCF101](https://docs.voxel51.com/dataset_zoo/datasets/ucf101.html). The LeRobot importer re-encodes to H.264/yuv420p automatically — [LeRobot importer](https://docs.voxel51.com/plugins/plugins_ecosystem/fiftyone_lerobot_importer.html). FFmpeg must be installed to work with video datasets — [FiftyOne FAQ](https://docs.voxel51.com/faq/)
- **CVAT video:** the server accepts any format ffmpeg reads (MP4, AVI, MOV) — [CVAT Overview](https://docs.cvat.ai/docs/getting_started/overview/). Chunks are video segments by default, or ZIPs of decoded frames with `use_zip_chunks` — [CVAT SDK DataRequest](https://docs.cvat.ai/docs/api_sdk/sdk/reference/models/data-request/). Zip chunks are larger but need no client-side decoding. The server stores both "original" and "compressed" quality (image_quality 5–100), and "use cache" prepares data on the fly — [CVAT: Tasks](https://docs.cvat.ai/docs/workspace/tasks-page/). Chunk type is chosen per (media_type, mode) in `task.py` — [task.py](https://github.com/opencv/cvat/blob/develop/cvat/apps/engine/task.py)
- **CVAT 3D:** requires a specific archive layout (`pointcloud/*.pcd` + `related_images/`, Velodyne `.bin`, or the default layout) — [CVAT: Tasks](https://docs.cvat.ai/docs/workspace/tasks-page/)
- **Label Studio:** video accepts .mp4 and .webm only, images accept bmp/gif/jpg/png/svg/webp, and audio, image and video must be referenced by URL. The docs warn against uploading media through the UI for large projects — [LS: Import data](https://labelstud.io/guide/tasks.html). I found no server-side transcoding in the docs.
- **QuPath WSI:** reads through Bio-Formats and OpenSlide. OpenSlide is "fast, lightweight… but restricted to 2D, 8-bit, RGB"; Bio-Formats handles z-stacks, time series and multiplexed images. DICOM WSI is supported through Bio-Formats 6.8.0 (QuPath ≥0.4.0) and OpenSlide 4.0 (QuPath ≥0.5.0). OME-Zarr is supported from 0.6.0. Z-stacks in NDPI work only with Bio-Formats, and on the Apple-silicon build Bio-Formats cannot read most NDPI files. Non-pyramidal TIFFs often fail — [QuPath: Supported image formats](https://qupath.readthedocs.io/en/stable/docs/intro/formats.html). The "auto-generate pyramids" option builds pyramids dynamically for large single-resolution images — [QuPath: Projects](https://qupath.readthedocs.io/en/stable/docs/tutorials/projects.html). The OpenSlide reader is `OpenslideImageServer` — [QuPath 0.7.0 javadoc](https://qupath.github.io/javadoc/docs/qupath/lib/images/servers/openslide/OpenslideImageServer.html)
- **OHIF WSI:** the microscopy extension wraps `dicom-microscopy-viewer` (the library behind the SLIM viewer) for DICOM VL Whole Slide Microscopy and "runs fully client side without any custom server components" — [OHIF dicom-microscopy README](https://github.com/OHIF/Viewers/blob/master/extensions/dicom-microscopy/README.md). (Secondary) Tiles are fetched on demand via WADO-RS at the current zoom level — [DeepWiki: OHIF Microscopy](https://deepwiki.com/OHIF/Viewers/6.6-microscopy-and-wsi)
- **WSI → DICOM conversion:** `wsidicomizer` converts SVS, NDPI and Philips TIFF losslessly, CZI lossily, and MRXS/SCN/BIF and others lossily through the openslide extra and the Bio-Formats extra. It depends on pydicom, highdicom, imagecodecs, PyTurboJPEG, opentile and wsidicom. CLI: `wsidicomizer -i in -o out` — [imi-bigpicture/wsidicomizer](http://github.com/imi-bigpicture/wsidicomizer)
- **MONAI Label / OHIF NIfTI:** MONAI Label's local datastore takes NIfTI directly (`*.nii.gz`) — [MONAI Label README](https://github.com/project-monai/monailabel). Serving the same data to OHIF through Orthanc DICOMweb needs NIfTI → DICOM conversion with PyPlastimatch (a Plastimatch wrapper), which the official tutorial makes the user do — [MONAI tutorial: spleen segmentation with OHIF](https://github.com/Project-MONAI/tutorials/blob/main/monailabel/monailabel_radiology_spleen_segmentation_OHIF.ipynb)
- **HF datasets:** `Video` decodes lazily with `torchcodec.decoders.VideoDecoder`, `Nifti` with nibabel and `Pdf` with pdfplumber — [features.py](https://github.com/huggingface/datasets/blob/main/src/datasets/features/features.py). The Viewer backend converts every Hub dataset to Parquet ahead of time and serves rows from a precomputed cache — [HF Dataset viewer docs](https://huggingface.co/docs/dataset-viewer/en/index)
- **napari:** conversion is left to reader plugins. `get_reader` should check cheaply (e.g. for a `zarr.json` file or magic bytes) and return a reader, and napari's built-in reader settings include lazy loading via dask above a size threshold — [napari: Plugin contributions](https://napari.org/stable/plugins/building_a_plugin/guides.html); [napari manifest reference](https://napari.org/stable/plugins/technical_references/manifest.html)

### Inferences
- When an editor relies on the browser's native decoder (`<video>`), conversion becomes either the user's job (FiftyOne, Label Studio) or a server-side ingest step (CVAT, the FiftyOne LeRobot importer). A product that wants "drop any file in a folder" needs a server-side ingest/convert stage per format (ffmpeg for video; OpenSlide, libvips or wsidicomizer for WSI; DICOM ↔ NIfTI tools) and should keep the original next to the derived, browser-ready copy, as CVAT does with original and compressed chunks.

### Gaps
- I found no source on whether CVAT or FiftyOne tile WSIs. Neither appears to support WSI natively. FiftyOne treats `.tiff` as a plain image according to the skills file.
- I did not verify libvips, tiffslide or DeepZoom/IIIF use in any of the tools in scope. They are not mentioned in the docs I read. Digital Slide Archive / HistomicsTK (MONAI Label's pathology viewer) was not investigated.
- I did not research 3D Slicer's own DICOM import (DICOM database, pydicom/DCMTK plugins) or highdicom use for SEG export in MONAI Label.

## Q5. What design discussions exist about mixing data types in one project, and what did maintainers decide?

### Takeaway
Maintainers have consistently kept the unit of work homogeneous and moved mixing up to a container. CVAT uses projects that share a label spec, does not allow 1D/2D/3D in one project, and left the hanging-protocol request open. FiftyOne added grouped datasets with homogeneous slices, plus `unknown`/custom media types in 1.5.0. Prodigy recommends separate sessions and datasets. Roboflow's project type is permanent. Viewer-centric projects (OHIF, napari) built extension points (SOP class handlers and modes, reader plugins) rather than containers.

### Cited Findings
- **CVAT:** the maintainer's position is to use projects to aggregate data around one annotation spec and to create a new task for more data — [cvat-ai/cvat#9758 (2025)](https://github.com/cvat-ai/cvat/issues/9758). Bulk upload of many videos became "create multiple tasks when uploading multiple videos" (PR #4824), i.e. one task per video rather than mixed tasks — [opencv/cvat#916](https://github.com/opencv/cvat/issues/916). The hanging-protocol request has been open since 2022 — [cvat-ai/cvat#4648](https://github.com/cvat-ai/cvat/issues/4648). The 1D/2D/3D project rule is in the docs — [CVAT: Projects](https://docs.cvat.ai/docs/workspace/projects/)
- **FiftyOne:** homogeneous datasets, groups for mixing, with the rule that "each slice… must have a homogeneous media type" — [FiftyOne: Groups](https://docs.voxel51.com/user_guide/groups.html). `unknown` and custom media types were added in 1.5.0 for samples outside the built-in types — [FiftyOne: Using datasets](https://docs.voxel51.com/user_guide/using_datasets.html). PR #4101 made the metadata schema cover the fields of every slice media type in mixed groups — [voxel51/fiftyone#4101](https://github.com/voxel51/fiftyone/pull/4101). The 1.15.0 release (May 2026) improved support for sparse and imbalanced groups (not every group has every slice) — [release notes](https://docs.dev.voxel51.com/release-notes.html)
- **Label Studio:** an early issue (#40) proposed arrays of `label_config` per project, i.e. several UIs per project. The thread shows no adoption, and the current docs still describe one labelling configuration per project — [HumanSignal/label-studio#40](https://github.com/HumanSignal/label-studio/issues/40); [LS setup](https://labelstud.io/guide/setup)
- **Prodigy:** the maintainers advise against combining dependent annotation types in one interface and recommend separate passes and datasets — [Prodigy support #3031](https://support.prodi.gy/t/multiple-annotation-types-on-the-same-data/3031); [Prodigy support #7168](https://support.prodi.gy/t/how-to-setup-prodigy-for-several-tasks-on-the-same-data-points/7168)
- **Roboflow:** the project type is permanent, and you convert by exporting and re-importing — [Roboflow forum](https://discuss.roboflow.com/t/does-project-type-matter/131)
- **MONAI Label:** it is split into one app per domain (radiology, pathology, endoscopy) with a different recommended viewer for each, rather than one mixed app — [MONAI Label README](https://github.com/project-monai/monailabel)
- **OHIF:** the docs describe a "general pattern" in which "a mode can define which Viewport to use for which specific SOPClassHandlerUID, so if you want to fork just a single Viewport component for a specialized mode, this is possible" — [OHIF: Viewport module](https://docs.ohif.org/llm/platform/extensions/modules/viewport.md)

### Inferences
- On the question behind this research: the evidence supports one repository or project of files where the renderer is chosen per file (as in FiftyOne, OHIF, QuPath, HF and napari) for browsing and storage. Every labelling tool, though, scopes the ontology, tools, QA and export to a homogeneous unit. A hybrid fits the precedents best: one project or repository with per-file renderers, plus per-data-type workspaces or modes. Those workspaces would be like OHIF modes or FiftyOne flattened `select_group_slices()` views, opened over homogeneous subsets when labelling, running QA or exporting. Neither the "one studio per data type" design nor the "one universal editor" design has strong precedent on its own.
- Grouping (FiftyOne `Group`, OHIF study) is the established answer for multi-modal items that belong together, such as patient studies or sensor rigs. It sits on top of the per-file media type rather than replacing it.

### Gaps
- I found no formal RFC from any of these projects that compares "a project per modality" with "a mixed project". The evidence is docs rules, maintainer comments and code.
- I did not find public Label Studio maintainer statements on mixed-modality task lists (e.g. some tasks image-only and others text-only under one config).
- 3D Slicer's own data model (MRML scene of mixed nodes: volumes, segmentations, models, markups, each with its own displayable manager) was not researched in this pass. It is relevant prior art for a per-node renderer.
